## 0. 结论先行（TL;DR）

| # | 结论 | 置信度 | 关键证据 |
|---|---|---|---|
| C1 | **HwMonkeyTest 完全没有音频/录音测试**：3 个 JNI 库只操作 `/dev/hr8833`(云台) / `/dev/sn3732a`(灯) / `/dev/rtc0`(RTC)，dex 内无任何 `AudioRecord/MediaRecorder/AudioTrack` 调用 | 确定 | 全量 smali grep 音频 API = 空；so strings 只见三条设备节点 |
| C2 | **SoundRecorder 用 `MediaRecorder`，AudioSource = `MIC`(1)**（非 VOICE_COMMUNICATION/VOICE_RECOGNITION）；AMR-NB 编码、8kHz 默认、无显式采样率/声道设置 → HAL 走 **main mic**（`Capture MIC Path=Main Mic`），与 mixer_paths.xml 一致 | 确定 | `Recorder.smali:563` `const/4 v4,0x1` → `:620 setAudioSource(v4)` |
| C3 | **fsmeeting 存在两条独立采集链**：① Java 层 `RecordRunnable` 用 `AudioRecord(MIC,44100,STEREO,PCM16)` 做能量/分贝与 DOA；② native 层 `libavdevice.so` 用 **OpenSL ES**(`slCreateEngine`+BufferQueue) 采集，并 **dlopen 链入 libRealAudio.so** | 确定 | `RecordRunnable.smali:47-73`；libavdevice NEEDED + 字符串偏移 |
| C4 | **`libRealAudio.so` 是纯软件音频前端算法库（AEC/AGC/VAD/DOA 波束成形 + WebRTC 重采样）**，只吃 `short*` PCM，**不 open /dev/snd、不操作 ES7243/ES8316 寄存器、不 ioctl GPIO/功放**（唯一 import 是 `fopen@LIBC`） | 确定 | nm -D 导出符号；全量 strings 无 es7/i2c/codec；Thumb-2 反汇编 `OpenRealAudio` 仅 new/初始化 |
| C5 | **三款 APK 都没有任何"绕开 Android 音频 HAL"的直接硬件访问**：没有直接 open ALSA pcm 节点做 ioctl、没有 codec 寄存器操作、没有 ES7243 I2C 读写、没有功放 GPIO 控制。所有采集/播放都经标准 `AudioRecord`/`MediaRecorder`/OpenSL ES → Audio HAL | 高 | 见 §2-§4 全链路；`/dev/snd/` 在 fsmeeting 里仅用于 `File.list().length` 判断 USB 声卡数量 |
| C6 | **对"原厂能录音、mainline 不能"的解释**：APK 侧证据支持"原厂录音链完全依赖 vendor Audio HAL + 内核驱动的 `Capture MIC Path=Main Mic` 路径"。mainline 换 dummy codec 后该枚举控件及其背后路由丢失 ⇒ 与 speaker 无声**同源**（参见已有报告《音频-原厂HAL控件表逆向-20261116.md》）。APK 中**没有可抄的"隐藏 ioctl/寄存器序列"** | 高 | C1-C5 + mixer_paths.xml + HAL 报告 §5 |
| C7 | **对"ES7243 是否原厂麦克风真实链路"的提示**：APK 证据**不能直接证明**物理 mic 是 ES7243 还是 ES8316 模拟 mic——因为所有采集都是标准 source，APP 对 PCM 来自哪个芯片无感知。但提供了两条**强提示**：① `libRealAudio.so` 的 DOA 算法（`Coordinates of microphones, relative to Mic0`）是**纯软件**，输入是**标准双声道 PCM**，说明所谓"麦阵"波束成形是在应用层用通用 2ch 数据做的，**不要求专用多通道 mic 硬件节点**；② 原厂 capture path 只有单条 `Main Mic`，ES8316 vendor 驱动本就有 `main_mic_capture` controls（`Differential Mux`=0）。⇒ **ES7243×2(I2S) 很可能不是原厂录音的必经链路**；原厂"Main Mic"更可能是 ES8316 自带 ADC 的模拟 mic 或 SoC 侧 2ch 输入。此项为**推断**，需硬件/内核侧进一步证实 | 中 | C4/C5 + HAL 报告 §3.1 e21/e22 + 已有 ES7243 报告（SDOUT 恒 0xFFFF、芯片停在 0x60） |

> **一句话**：从 APK 层挖不到任何"音频/麦阵的硬件后门"——三款 App 全走标准 Android 音频框架。原厂能录音靠的是 vendor HAL 的 `Main Mic` 路径，mainline 要补的是 **HAL/内核的 capture 路由与 codec 驱动对齐**，而不是从 App 里找寄存器或 ioctl。ES7243 的 SDOUT 问题更像是**在错误的芯片上找信号**。

> **⚠ 11:13 更正（见综合研判 §2）**：上文 C6 及 §6.1 里"mainline 换 dummy codec 后 `Capture MIC Path` 枚举及背后路由丢失 ⇒ 与 speaker 同源"的推断**已推翻**——全 vendor kernel.img + ramdisk 都搜不到 `Playback Path`/`Capture MIC Path`/`Main Mic` 控件，vendor es8316 用的是标准 ES8316 控件名，path 枚举的实现端不在这份内核里。APK 层"无硬件后门"的结论不受影响，但**不能再把 path 控件丢失当作无声根因**。

### 5.5 判定

`libRealAudio.so` **不碰硬件**：它接收已经由 OpenSL ES/AudioRecord 采集好的 PCM（通常 16kHz/48kHz），做 AEC（需要 far-end 参考 `AddFarend`）、AGC、VAD、DOA。`RealGetAngle` 的结果经 `ConfDataContainer.getMicAngle()` 回传到 Java（`AudioCaptureDetectHelper.smali:76-110`：`float-to-int`，`-999`=无效，`90`=正前方，转成 `turnAngle` 控制云台转向说话人）。

**这对麦阵移植的含义**：原厂所谓"麦克风阵列"是**软件波束/DOA 算法 + 通用双声道 PCM 输入**，不是靠 ES7243 硬件做多通道同步采样后交给专用驱动。算法层对"这 2ch 来自 ES8316 模拟 mic 还是 ES7243 I2S"完全无感。

## 6. 对 mainline 的指导意义（结论 C6/C7 展开）

### 6.1 能解释"原厂能录音、mainline 不能"吗？——**间接能，且指向与 speaker 同源**

1. **APK 层没有任何可抄的硬件操作**。三款 App 全部把采集交给标准框架（`AudioRecord`/`MediaRecorder`/OpenSL ES）。所谓"原厂录音"的差异化全在 **vendor Audio HAL (`audio.primary.rk30board.so`) + 内核 es8316 驱动** 内部：HAL 收到 `AudioSource.MIC` → 下发 `Capture MIC Path=Main Mic` → vendor 驱动完成 mic 偏置、ADC 使能、路由。
2. mainline 6.18 换 dummy codec / 丢掉枚举控件后，`Capture MIC Path` 及其背后逻辑一并消失 ⇒ 与 speaker `Playback Path=SPK` 丢失是**同一个根因**（见《音频-原厂HAL控件表逆向-20261116.md》§5）。
3. **可直接复用的最小验证**：`AudioRecord(MIC, 44100, CHANNEL_IN_STEREO, PCM_16BIT)` 与 `MediaRecorder(AudioSource.MIC, AMR_NB)` 是原厂确已工作的配置。mainline 上先用 `tinycap`/`arecord -D <hw> -f S16_LE -r 44100 -c 2` 打通 I2S capture，再对齐 HAL 的 input source 映射，这是比调 ES7243 寄存器更高优先级的方向。

### 6.2 是否提示 ES7243 不是原厂麦克风真实链路？——**是（提示级，非证明级）**

支持该提示的证据：
- **无直接硬件证据**：三款 APK + 全部 so 均无 ES7243 I2C 地址(0x10/0x12)、无 es7243 字符串、无多通道 mic 节点 open。如果 ES7243 是原厂主 mic，其配置必然在 vendor 内核/DTS，而非 App——这与 ES8316 speaker 的情况一致。
- **capture path 是单条 `Main Mic`**（mixer_paths.xml + HAL 报告 e21 `main_mic_capture`），不是"Mic Array"/"Multi Mic"；ES8316 codec 本身含 ADC，`Differential Mux=0` 即 main mic 路径。
- **麦阵是算法不是硬件**：libRealAudio 用通用 2ch PCM 做 DOA（`Coordinates of microphones, relative to Mic0`），不要求 ES7243 的多芯片同步采样。
- **ES7243 侧已穷尽软件手段仍 SDOUT 恒 0xFFFF、芯片停在未上电态 0x60**（见《麦阵-ES7243-MCLK破案与软件侧穷尽-20261117.md》）——与"走在错误芯片上"的假设一致。

**建议的判定路径**（不改系统、仅研究/测量）：
1. 从 vendor `mixer_paths.xml`/HAL 确认 `Main Mic` 对应的 kcontrol（如 `Differential Mux`）在 vendor 内核里接到 **ES8316 的 ADC 输入**还是 **I2S0 RX(ES7243)**。
2. 查 vendor DTS/驱动源码（`/mnt/stock` 或 SSH 只读）：搜 `es7243`/`mic-array`/`i2s0` 与 `es8316` 的 link，确认 I2S0 RX 在 stock 上是否真的被启用为 capture。
3. 硬件测量（用户既有计划）：ES8316 是否有模拟 mic 输入走线；ES7243 SDOUT 到 SoC SDI0 是否连通。
4. 若 stock capture 根本没用 I2S0 RX，则 ES7243 移植应**降优先级**，先把 `AudioRecord(MIC,44100,STEREO)` 在 mainline 用 ES8316/模拟 mic 路径打通。

### 6.3 置信度说明

| 事项 | 置信度 | 说明 |
|---|---|---|
| 三款 APK 无直接音频硬件操作 | 高（确定） | 全量 smali/so strings/nm 交叉验证 |
| 原厂能录音靠 vendor HAL 的 Main Mic 路径 | 高 | APK 标准 source + mixer_paths + HAL 报告三重印证 |
| ES7243 不是原厂主 mic 真实链路 | 中（提示） | APK 不能直接点名物理芯片；需内核/DTS/硬件证实 |
