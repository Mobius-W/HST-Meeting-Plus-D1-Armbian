# 适配过程：从原厂 Android 到 Armbian

> 本文记录 HST Meeting Plus D1 的完整适配路径。每阶段给出：目标 → 动作 → 验证 → 结论。
> 取证过程中产生过大量被推翻的结论，本文**只写最终有效的路径**；弯路细节见文末"证据链文档索引"。

时间跨度：2026-11-08 ~ 2026-11-20。基线内核：`6.18.63-current-rockchip64`。

---

## 阶段 0：原厂系统备份（11-10）

**目标**：任何破坏性操作前，先拿到可回退的全盘镜像。

**动作**：
1. 板载微动按钮长按上电进 Loader，下 loader 后从 MaskROM/loader 读回 eMMC 全盘（7,820,083,200 B）；
2. 分区级备份 `system.img`（1,610,612,736 B）、`boot.img`、`resource.img`、`trust.img`、`uboot.img` 等；
3. ADB 导出基线（APK 列表、prop、build.prop、HAL 配置）；
4. 记录分区表 `PARTITIONS-AUTHORITATIVE.txt` 与 `parameter.txt`。

**验证**：全盘镜像 `rkdeveloptool wl 0` 写回后能正常起 Android（已实测救砖成功）。

**结论**：备份是可回退的地基。小分区镜像随仓库发布在 [`firmware/android-stock/`](../firmware/android-stock/)，全盘镜像因体积留本地。

## 阶段 1：硬件扫描与选型判定（11-10 ~ 11-15）

**目标**：搞清楚板上到底有什么，选对 Armbian 基线。

**动作**：
- 从原厂 DTB（`rk3399-mid-stock.dts`）反推 GPIO/I²C/寄存器绑定；
- 逐项确认实物：拆机看 DRAM 丝印、数按键、拍照认芯片丝印；
- 反编译原厂 APK（`fsmeeting`/`HwMonkeyTest`）与 `libJniioctl.so`，挖出云台/灯控的软件调用链；
- 对比 ophub 41 个 rk3399 板型数据库，判定最接近的参照。

**几个关键判伪**（这些弯路值得记下来）：

| 曾以为 | 实际 | 证据 |
|---|---|---|
| 4 GB DDR3-1600 | **4 GB LPDDR4**（2ch×2048 MB） | DRAM 丝印 + TTL 训练日志双证 |
| SN3732A 是功放 | **氛围灯控制器** `@ i2c6 0x50/0x52/0x53` | 原厂 APK 的 `libJniledctl.so` 导出 `LedredOn/LedgreenOn/...` |
| 有 ES8316 codec | **板上没有这颗芯片**，vendor DTS 是空壳节点 | 0x11 永远 NAK；mainline 真驱动一碰就 210 条 `ASoC error(-6)` |
| ophub 固件可直接用 | 不适用，须走 armbian 官方源码 | 见 `docs/ophub-固件选型.md` §十六 |

**结论**：以 `armbian/build` 官方源码为基线，参照 r432 AIO-3399C 的 vendor LOADER 阵营排版；自写板级 DTS。

## 阶段 2：Armbian board config + 首次适配（11-11 ~ 11-15）

**目标**：让内核和 U-Boot 能在这块板上编译并启动。

**动作**：
- 新增板级配置 [`armbian/userpatches/config/boards/rk3399-mid.csc`](../armbian/userpatches/config/boards/rk3399-mid.csc)：
  - `BOOT_SOC=rk3399`、`BOOTCONFIG=rock-pi-4-rk3399_defconfig`
  - `BOOT_FDT_FILE=rockchip/rk3399-mid.dtb`
  - 走官方 `binman-atf-mainline` 场景，产物是单个 `u-boot-rockchip.bin`
- 自写主 DTS [`rk3399-mid.dts`](../armbian/userpatches/kernel/archive/rockchip64-6.18/dt/rk3399-mid.dts)（eDP / HDMI / 触摸 / PMIC / 音频 / 云台 / LED / 摄像头）；
- DDR 初始化用官方 `rk3399_ddr_800MHz_v1.30.bin`，不手写 `sdram-params`；
- CI 工作流 `.github/workflows/build-armbian.yml` 云端编译，本机无需交叉工具链。

**验证**：`u-boot-rockchip.bin` 写入 LBA64 后 TTL 抓到 `DDR Version 1.30 → U-Boot → Starting kernel`。

**结论**：引导链独立于 Android，可独立刷写。写盘坐标纪律：mainline IDB → LBA64，FIT → LBA16384。

## 阶段 3：显示 / 触摸 / 电源 / 网络打通（11-16 ~ 11-17）

**目标**：把基础外设逐个点亮。

| 外设 | 动作 | 验证 |
|---|---|---|
| eDP 内屏 | DTS 面板节点 `neweast,wjfh116008a` + 背光 PWM0 | `card0-eDP-1 connected`，1920×1080，255 级背光 |
| HDMI | CRTC 锁定到 VOPB | 拔插线测试：HDMI 断开而 eDP 不挂死 |
| 触摸 GT9271 | i2c2 0x14 驱动绑定 | ID 9271 v1040，10 点，20 s 静置 0 误触、滑动 2532 事件 |
| 充电 / 电量计 | 原厂 `dc_det_gpio` 极性 ACTIVE_LOW 修正 | 插 DC 后 `ONLINE=1`、SOC 上升 |
| 风扇 / 温度 | `gpio-fan` + `tsadc` | `fan1_input=3000`，cpu/gpu 温度正常 |
| WiFi / BT | AP6255 `brcmfmac` | hci0 + wlan0 正常 |

**结论**：基础外设全绿。按键相关：`adc-keys`/`gpio-keys` 是参考设计残留，板上只有电源键（硬件直驱 LED）。

## 阶段 4：音频全链路闭环（11-16 ~ 11-19）★ 最大弯路

**目标**：喇叭、耳机、麦克风全部出声/录音。

**症状**：播放无声、录音全 `0xFFFF`、I²C 上 0x10/0x12 无 ACK，一度怀疑硬件损坏。

**真正根因**：DTS 里 `mic-array clocks` 写成 `SCLK_I2S0_8CH`（`0x56`，控制器内部时钟，**不上脚**），应为 `SCLK_I2S_8CH_OUT`（`0x59`，唯一输出到 GPIO4_A0）。芯片停在 datasheet 的 power-down（输出钳地）。

**动作**：
1. 逐字节核对 vendor 内核 ES7243 驱动的写寄存器序列；
2. 对照 ES7243 PB / ES7148 DS 手册的 MCLK 先决条件；
3. 板上 `clk_summary` 看到 `clk_i2sout state=N` ⇒ 定位到 clock cell；
4. DTB `0x56 → 0x59`（用 [`tools/patch-dtb-micarray.py`](../tools/patch-dtb-micarray.py) 自动改）。

**验证**：

| 项 | 结果 |
|---|---|
| `clk_i2sout` | `prep=1 en=1 Y`，12.288 MHz |
| I²C 0x10/0x12 | ACK，16 寄存器可读 |
| `arecord` | rc=0，wav 576044 B，L/R 各有真波形（非恒 0xFFFF） |
| 全双工 | 播放《活着》同时录音，包络互相关 0.400@lag0.44 s |
| 喇叭 / 耳机 | 用户耳听确认 1 kHz 测试音与音乐正常；耳机左右声道都对 |

**耳机专项**：mainline 无 `rk_headset` 驱动 ⇒ HT4832 的 EN（GPIO4_D6=gpio158）UNCLAIMED 默认低 = 关断。已做 `ht4832-en.service` 常驻拉高。

**结论**：音频硬件全程完好；软件侧只需改 1 个 clock cell + 常驻耳机 EN。**不要再把"无声"归到芯片损坏**。

## 阶段 5：摄像头 IMX307 + rkisp1（11-17 ~ 11-19）

**目标**：MIPI 摄像头出图。

**动作**：
- vendor 内核 4.4 的 `imx307.c` 移植到 mainline 6.18（[`docs/camera/`](camera/) 下有源码与补丁）；
- 全链路 7 个 pad 设格式，isp:2 与 resizer 必须带 `crop`；
- sensor rebind（unbind/bind）触发 `__imx307_power_on` 自动灌寄存器表（67 项）；
- 参数由 Sony 官方 flyer + 原厂 cam_board.xml + vendor 驱动 + 高通平台调试博客四路交叉核对（37.125 MHz、2-lane RAW10、link-freq 222.75 MHz、frame_length_lines 1125=0x0465、0x301E=0xb2）。

**验证**：60 帧 248,832,000 B，30.00 fps，`complete_frames` 0→63，画面非死数据（mean 35.5 / std 12.4）。

**结论**：`-EPIPE` 是漏设 crop + 未 rebind，不是硬件问题。

## 阶段 6：云台 AT8833 逆向与驱动重写（11-16 ~ 11-19）

**目标**：驱动云台转动。

**过程**：
1. 挖出两条消费链：产线工具 `/dev/hr8833` ioctl、会议程序 `IoctlManager.turnByAngle` 按 DOA 每秒调整；
2. 原厂是 240 ms 脉冲控制（摇杆 10°/次、声源定位 40 ms/度），**不是持续通电**——推翻早期"ocp=1→硬件坏"的判词；
3. 丝印更正：芯片是 **AT8833**（杭州中科微），不是 HR8833，二者仅 pin 兼容，参数差异大（VM 2.7–15 V，12 V 合规）；
4. 绕过驱动的用户态直驱实验证明：故障与驱动实现无关，**重写驱动修不好硬件**；
5. 驱动仍重写为 v2.1：移除 20 kHz 软 PWM（与芯片 50 kHz 斩波冲突）、固定 2 ms 唤醒、内建 `irq_stat` 边沿统计、`auto_reset` 默认关。

**当前状态**：一建立输出电位差即过流、惰行即恢复；三条控制路径（用户态直驱 / vendor ioctl / sysfs speed）行为一致。板上编译链已打通（[`tools/build-onboard.sh`](../tools/build-onboard.sh)），`vermagic` 与在跑内核完全匹配。

**遗留**：需断电实测 `AOUT1↔GND` / `AOUT2↔GND` / `AOUT1↔AOUT2` 阻值，定位是板级短路还是芯片损坏。详见 [`docs/云台-消费端-测试工具与会议程序-20261119.md`](云台-消费端-测试工具与会议程序-20261119.md) §12–§14。

## 阶段 7：当前状态（2026-11-20）

**已打通**：SoC / 内存 / eMMC / RK808 / 电量计 / 充电 / 风扇 / 温度 / eDP / HDMI / 背光 / 触摸 / 音频录放 / 耳机 / 喇叭 / IMX307 摄像头 / rkisp1 / GPU / VPU / 解码 / RGA / IEP / WiFi / BT / USB。

**部分可用**：氛围灯（寄存器语义待逆向）、耳机检测（无 `rk_headset` 驱动）、NTC 温控。

**未解决**：云台电机（过流，疑硬件）。
