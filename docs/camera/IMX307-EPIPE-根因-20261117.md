## 二、根因（源码级钉死）

mainline v6.18 `drivers/media/platform/rockchip/rkisp1/rkisp1-csi.c`：

```c
static int rkisp1_csi_s_stream(struct v4l2_subdev *sd, int enable)
{
    ...
    source = media_entity_to_v4l2_subdev(source_pad->entity);
    if (!source)
        return -EPIPE;

    asc = v4l2_async_connection_unique(source);   // ← :381
    if (!asc)
        return -EPIPE;                            // ← :383，就是这里
```

`rkisp1_isp.c:979` 再往下调 `v4l2_subdev_call(rkisp1->source, video, s_stream, true)`，
错误原样冒泡成 `start pipeline failed -32`。

而本板 imx307 驱动注册用的是老 API（`0002-media-i2c-add-imx307.patch:1003`）：

```c
ret = v4l2_async_register_subdev(sd);
```

它**只注册 subdev，不创建 `v4l2_async_connection`**。所以 media graph 的 link 全是
`ENABLED`（那是 fwnode graph 解析出来的），sensor probe 也成功，但一 STREAMON，
`v4l2_async_connection_unique(source)` 返回 NULL ⇒ `-EPIPE`。

**这不是时钟、复位、供电、PHY 问题**——那三层 run19 已经全修好了：
37.125 MHz 有、reset 极性对、DTS pinctrl 生效、sensor 在总线上应答。

## 三、修法（已落地到本地，尚未生效）

`include/media/v4l2-async.h:318-337`（v6.18）明确：

> `v4l2_async_register_subdev_sensor()` — like `v4l2_async_register_subdev()` with the
> exception that calling it will also parse firmware interfaces for remote references
> using `v4l2_async_nf_parse_fwnode_sensor()` and registers the async sub-devices.

本板 DTS 里 sensor 节点已有完整 endpoint（`remote-endpoint = <&mipi_in_imx307>`、
`data-lanes = <1 2>`、`link-frequencies = <222750000>`，见 `rk3399-mid.dts:825-831`），
正好满足它的解析要求。

改动就一行（`0002-media-i2c-add-imx307.patch:1003`，1:1 替换，**hunk 行数 1066 不变**）：

```diff
-	ret = v4l2_async_register_subdev(sd);
+	ret = v4l2_async_register_subdev_sensor(sd);
```

`v4l2_async_unregister_subdev(sd)` 在 remove 路径里仍适用，不用动。

## 五、2026-11-17 19:0x 追记（run20 刷机后，纠正本节二/三的判断）

> ⚠ **下面这段推翻本文件 §二/§三 的结论**。run20（commit `19bb039`）已把
> `v4l2_async_register_subdev_sensor()` 编进 imx307.ko 并刷机验证，
> `-EPIPE` **并没有因此消失**。§二 关于「async connection 缺失」的根因判断是错的。

### 5.1 -EPIPE 的真正根因：链路格式不匹配

开 dynamic debug（`echo 8 >/proc/sys/kernel/printk`；
`echo "file v4l2-subdev.c +pflmt" >/sys/kernel/debug/dynamic_debug/control`）后 dmesg 铁证：

```
v4l2_subdev_link_validate_default: width does not match (source 1920, sink 800)
v4l2_subdev_link_validate_default: height does not match (source 1080, sink 600)
v4l2_subdev_link_validate_default: media bus code does not match (source 0x3012, sink 0x300f)
link was "imx307 4-001a":0 -> "rkisp1_csi":0
rkisp1 ff910000.isp0: start pipeline failed -32
```

sensor 原生 `SRGGB12_1X12/1920x1080@10000/300000`（0x3012），
而 csi sink 停在 800x600 / 0x300f。`video_device_pipeline_start()` 做 link validate
时发现两端 fmt 不一致，返回 -EPIPE，**跟 async 框架无关**。

`v4l2-ctl --set-fmt-video` 只设 capture 节点，不会往 subdev 传播；必须用 `media-ctl`
逐 pad 设置（sensor → csi → isp → resizer），且 isp:2 要 fmt+crop 一起设否则回退。
命令见 `.workbuddy/memory/2026-11-17.md` 19:0x 节。

### 5.2 设备节点已重排（旧文档 video5/6 作废）

```
rkisp1   = /dev/media0 + /dev/video0(mainpath) /video1(selfpath) /video2(stats) /video3(params)
rkvdec   = /dev/media2 + /dev/video8
rga      = /dev/video5
vpu-enc  = /dev/video6 /video7
```
任何验证前先 `v4l2-ctl --list-devices` 现场确认，别硬编码。

### 5.3 最终定性：软件链路全通，卡在物理层

按 5.1 统一格式后：link validate 全部通过、pipeline 成功 start，dmesg 打出
`rkisp1_rsz_config` / `rkisp1_csi_config`（`MIPI_CTRL=0x61f00`、
`MIPI_IMG_DATA_SEL=0x2c`、`MIPI_STATUS=0x2000`），`MIPI_STATUS=0x2000` 说明 CSI 逻辑在跑。

但抓帧仍 0 字节，ISP debugfs 计数器给出铁证：

```
/sys/kernel/debug/ff910000.isp0/input_status     → vsync: 0, hsync: 0
/sys/kernel/debug/ff910000.isp0/complete_frames  → 0
```

I2C 此时 `i2ctransfer` 报 `Device or resource busy` ⇒ sensor 已被驱动占着、处于 streaming 态，
但 D-PHY 一个像素都没送进 ISP。

**结论：摄像头出图卡在物理层（D-PHY / sensor MIPI 输出 / 差分线 / 供电复位时序），
不是软件配置问题。** 与 WF7000A HDMI PHY PLL 同类。不要继续改 DTS 或 patch 猜，
需要硬件实测：量 MIPI 差分线、sensor 各路供电、复位时序、37.125 MHz 参考时钟的实际波形。
数字人分支维持关闭。

## 六、2026-11-17 19:2x–19:4x 决定性翻案（§5.3「物理层问题」作废）

> ⚠ **本节推翻 §5.3 的「物理层无数据」定性。** 那是错的。不需要硬件实测，
> 不需要示波器，不需要改 DTS。**根因是驱动初始化表在 probe 写完就被下电清空。**

### 6.1 起因：从原厂 Android 固件挖参数

用户问「安卓固件里有参数挖吗」。三个来源全挖到：

| 来源 | 文件 | 关键参数 |
|---|---|---|
| 原厂 system.img（loop 挂 `/mnt/stock`） | `etc/cam_board.xml` | i2c4@0x1a、MCLK 37.125 MHz、2-lane、RAW10、1920×1080@30、RST=GPIO1_B0、PWDN1=GPIO1_B1、供电全 NC |
| 原厂 4.4 驱动源码 | `imx307.c.vendor-4.4` | **67 项 `imx307_global_regs[]` 初始化表**、link_freq 222.75 MHz、SRGGB12 |
| 原厂 DTB 反编译 | `rk3399-mid-stock.dts:3696` | ISP0/ISP1 均 okay、cif_clkout=GPIO2_B3 func3（与现 DTS 一致） |

### 6.2 决定性对照实验（全程非破坏性，未刷机/未改 DTS/未重启）

**Step 1 — streaming 态逐项读 sensor 寄存器，发现大面积不匹配原厂表：**

| 寄存器 | 原厂表 | 实机 | 说明 |
|---|---|---|---|
| `0x3009` | `0x02` | `0x01` | RAW 位宽/输出格式控制 |
| `0x3011` | `0x0A` | `0x00` | MIPI 配置 |
| `0x3480` | `0x49` | `0x92` | PLL/时序 |

CHIP_ID `0x301e=0xb2` 正确、reset 已拉高、I²C 可读写 ⇒ sensor 活着，
但寄存器是**默认值**，初始化表没生效。

**Step 2 — 手动灌入 67 项原厂表（`/tmp/imx307_write.sh`，脚本已从原厂源码提取）：**
回读 `0x3009=0x02` / `0x3011=0x0a` / `0x3480=0x49` 全部写入成功。

**Step 3 — 关键对照（同一链路格式、同样 6 秒窗口）：**

```
灌表 + stream   → complete_frames: 0 → 1155（持续出帧，st3.log 显示 30.00 fps）
不灌表 + stream → complete_frames: 1155 → 1155，delta = 0
```

抓到 1.5 GB YUYV（478+ 帧）。单帧转 PNG 偏暗（mean=29, std=1.2, min=23, max=54）——
夜间暗环境所致，非全零死数据。RAW10/RAW12 两种链路都能出帧 ⇒ 位宽不是卡点。

### 6.3 根因（源码级钉死）

mainline 移植版 `imx307_probe()`（patch:964）里调用
`imx307_write_array(client, imx307_global_regs)` 写表，但 probe 尾部
`pm_runtime_set_suspended()` 把 sensor 下电。sensor 寄存器是 **volatile**，
掉电即丢失 ⇒ 表白写。

vendor 原版（4.4）是在 `s_power(on)`（`imx307.c.vendor-4.4:648`）里写表，
**每次上电都重写**，所以原厂 Android 正常工作。

### 6.5 澄清 PWDN1 与位宽疑点

- **PWDN1（GPIO1_B1/gpio41）**：sysfs/GPIOD 写高读回 0，`pinconf` 显示
  `input bias pull up, output drive strength 6mA`。但 sensor I²C 能通、能出帧
  ⇒ PWDN 非卡点（若真生效 I²C 都读不到）。DTS 注释「常开不声明」成立。
- **RESET（GPIO1_B0/gpio8）**：stream 关闭后驱动拉低（runtime PM 下电），
  STREAMON 时拉高——正常行为。rebind 后若不重设 media 链路格式会 -EPIPE。
- **位宽**：`cam_board.xml` 写 RAW10、vendor 驱动用 SRGGB12，实测两者都能出帧，
  不是卡点。修复后若图像偏色再回来看 `0x3009` 取值。
