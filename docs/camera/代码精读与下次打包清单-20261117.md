### 3.1 `USED_TEST_PATTERN` 宏未定义 → test pattern 路径是死代码

patch 里 test pattern 相关代码全部被 `#ifdef USED_TEST_PATTERN` 包住（patch:76-80 / 135-137 / 250-258 / 446-461 / 754-758 / 836-841），但 **没有任何地方 `#define USED_TEST_PATTERN`**（csc、Makefile、Kconfig 全查过）。后果：

- `V4L2_CID_TEST_PATTERN` 控制项根本不创建；
- 上一轮板上手动写 `0x5e00=0x80` 回读 0x00——说明**即便启用 control，这颗 sensor 的 test pattern 寄存器也未必可写**（可能需特定 standby 时序或该型号不支持）；
- 无法用彩条测试图案做不依赖环境光的出图验收。

**本轮决定：不启用（保持 `#ifdef` 关闭）**。理由：

1. 彩条功能未经验证（寄存器回读失败），把它编进一个**已经验证能编、能出图**的 patch 是净风险；
2. 去掉 6 处 `#ifdef` / `#endif` 会改变 hunk 行数，必须重算 `@@ -0,0 +1,1068 @@`，进一步增加打包失败面；
3. 出图验收已有硬指标 `complete_frames 0→1155 + 30.00 fps`，不依赖彩条。  
   若将来确需彩条，正确顺序是：先在板上用 i2ctransfer 验证 `0x5e00` 能写入并回读，再启用 control。

### 3.2 Kconfig 依赖不完整：`VIDEO_V4L2_I2C` / `V4L2_CCI_I2C` 未 select

`0002` patch 的 Kconfig 只写了 `select VIDEOBUF2_V4L2` / `select V4L2_ASYNC`。但驱动：

- 用 `v4l2_i2c_subdev_init()` / `v4l2_i2c_subdev_set_name()` → 需要 `CONFIG_VIDEO_V4L2_I2C`；
- 当前靠 csc 的 `opts_y+=CONFIG_VIDEO_V4L2_I2C` 兜着。

风险：将来换板/换 defconfig 时如果漏了这一行，编译会报 undefined reference。**建议**在 Kconfig 里补 `select VIDEO_V4L2_I2C`（注意它是 bool），这样 csc 里那行可以删掉，依赖自洽。`V4L2_CCI_I2C` 当前驱动没直接用（用的是自己的 `i2c_master_send`），保留在 opts_m 只是为将来改用 regmap/cci 预留，可不动。

## 四、精读发现但**不建议改**的 3 项（附理由，避免下次误改）

### 4.1 `link-frequencies=222750000` 与 `IMX307_LINK_FREQ=222750000` 看似差一倍——实际不差

官方文档 `video-interfaces.yaml:192-197` 明确：`link-frequencies` 是 **actual frequency of the bus, not bits per clock per lane**。对 MIPI CSI-2 DDR，总线频率 = bit rate/lane ÷ 2。

- 原厂注释 `mipi_datarate per lane 445.5Mbps` ⇒ 总线频率 = 445.5/2 = **222.75 MHz**；
- 我们 DTS 写 `222750000`、驱动 `V4L2_CID_LINK_FREQ` 写 222750000 —— **与官方定义一致**。

对照 imx290（v6.18 上游）2-lane 1080p 用 `445500000`，那是它的实际 bus 频率（891 Mbps/lane ÷ 2），与 IMX307 是不同 sensor 的不同速率，**不能照抄**。pixel_rate = 222.75M×2×2/12 = 74.25 Mpx/s，HBLANK=(4400−1920)=2480，一帧总像素 4400×1125=4.95M，30fps 需要 148.5 Mpx/s —— 这里数字对不上，但 vendor 原版就这么写、且实测 30.00 fps 正常出帧，说明 RKISP1 侧用 DTS 的 link-frequencies 而非 V4L2 control 配 DPHY。**保留原值，不要动**；若将来要修帧率精度，应在 sensor 寄存器层调 PLL，不是改这两个宏。

### 4.2 `hts_def=0x1130(4400)` 与 global_regs 的 `0x3472/0x3473=0x079C(1948)` 不同——不是 bug

`0x3472` 在 STARVIS 系列是 **X_OUT_SIZE**（imx290.c:100 定义、:388 写 1920），不是 HTS。所以 1948≈1920+28 是输出宽度，与 hts_def 无关。`hts_def=4400` 是曝光控制的 HBLANK 基准值，vendor 原版一致。**保留**。

### 4.3 `devm_regulator_get_optional()` 返回 `ERR_PTR(-ENODEV)` 而非 NULL——已在 patch 处理

patch:897-908 有 `if (ret == -ENODEV) { consumer = NULL; continue; }`，注释完整。**已修，无需再动**。
