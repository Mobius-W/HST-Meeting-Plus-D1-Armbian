## 1. ★ 决定性证据：vendor DTS 的 mic 路由走模拟输入

`rk3399-mid-stock.dts:4212-4227` 的 `es8316-sound` 节点（反编译自原厂 DTB）：

```dts
es8316-sound {
    compatible = "simple-audio-card";
    simple-audio-card,format = "i2s";
    simple-audio-card,name = "rockchip,es8316-codec";
    simple-audio-card,mclk-fs = <0x100>;          // 256
    simple-audio-card,widgets = "Microphone", "Mic Jack",
                                "Headphone", "Headphone Jack";
    simple-audio-card,routing = "Mic Jack", "MICBIAS1",
                                "IN1P", "Mic Jack",
                                "Headphone Jack", "HPOL",
                                "Headphone Jack", "HPOR";
    simple-audio-card,cpu   { sound-dai = <0xd8>; };  // i2s@ff880000
    simple-audio-card,codec { sound-dai = <0xd9>; };  // es8316@11
};
```

**要点**：capture 走 `Mic Jack → MICBIAS1 → IN1P`——这是 codec **自带模拟 ADC 输入脚**，不是 `I2S0 RX`（ES7243 的 SDOUT 方向）。ES7243 的 DTS 节点（`es7243@10/@12`）只有 `compatible + reg`，**没有 `#sound-dai-cells`、没接进任何 sound card、没有 dai-link**。

对应 mainline 板上 DTB（`dtc -I fs /proc/device-tree`）：

```dts
rk3399-mid-sound {
    simple-audio-card,name = "rk3399-mid-es7148";
    simple-audio-card,format = "i2s";
    simple-audio-card,mclk-fs = <0x100>;
    simple-audio-card,frame-master = <...>;
    simple-audio-card,cpu   { sound-dai = <0xd0>; };  // i2s0
    simple-audio-card,codec { sound-dai = <0xd1>; };  // rk3399-mid-audio
};
rk3399-mid-audio {
    compatible = "rockchip,rk3399-mid-audio";
    everest,adc = <0xcd 0xce>;                        // 只有 ES7243×2 当 capture
};
```

**差异一句话**：原厂 sound card 的 codec = `es8316@11`（带模拟 mic 路由）；mainline 的 codec = 自写复合 codec `rk3399-mid-audio`，capture 只挂 ES7243×2。两者 capture 拓扑完全不同。

## 2. 交叉核实：path 枚举控件的实现端不存在（推翻旧结论）

此前 `音频-原厂HAL控件表逆向-20261116.md` 的结论是「原厂 speaker 播放唯一下发 `Playback Path=SPK`，mainline 换 dummy codec 后该枚举及其背后逻辑丢失 ⇒ 无声」。本次核实发现该链条缺了实现端：

| 检查对象 | 方法 | `Playback Path` / `Capture MIC Path` / `Main Mic` |
|---|---|---|
| `stock/kernel.img`（Linux 4.4.83 ARM64 Image） | `strings -a` 全镜像 | **0 命中**（`SPK` 有 10 处，均为无关串） |
| `stock/boot.img` ramdisk（gzip→cpio 解包，实际仅 `drmboot.ko`/`rk30xxnand_ko.ko`） | 解包后 `grep -ra` | **0 命中** |
| 标准 ES8316 控件名 | `strings` | 大量存在（`Differential Mux`/`Line input PGA`/`Left Hp mux`/`Playback Polarity`…） |

⇒ vendor es8316 驱动用的是**标准 ES8316 控件**，不实现 HAL 那套 path 枚举。HAL 侧下发 path 是真的，但接收端要么在 HAL 自己内部消化、要么在另一个未打包进本镜像的模块里。**结论：不能再说"mainline 丢 path 控件 = 无声根因"**。

## 3. ⚠ 必须承认的矛盾（不要掩盖）

§1 的"原厂 capture 走模拟 mic"与另一批硬事实冲突：

- 实物 DAC 已钉死 = **ES7148**（QFN-12，纯 I2S 输入、**无 I2C、无寄存器、也无 ADC**）；
- 所谓 vendor `es8316` 驱动是**空壳/魔改**（`everest,es8316` 空壳节点 + 两个 GPIO `spk-con`/`amp-en`，靠 GPIO 而非寄存器控制）；
- 但用户实测 **Android 下麦克风能录**。

若 codec 侧真是"没有 ADC 的 ES7148"，那 DTS 里的 `IN1P`/`MICBIAS1` 路由只是沿用 Rockchip SDK 模板的空壳（无物理意义），原厂实际录音**只能**来自 I2S0 RX = ES7243。这与 §1 的 DTS 字面结论相反。

**如何裁决（按优先级，均不需刷机/拆机）**：

1. 在 vendor kernel.img 里确认 `es8316` 驱动是否真的实现 capture DAI（有无 `IN1P`/`MICBIAS1` 对应的 kcontrol 读写与 ADC 使能）——本次反汇编只确认了 playback 侧 GPIO，capture 侧未定。
2. 查原厂 HAL `audio.primary.rk30board.so` 里 `get_input_device`/`Main Mic` 最终落到哪个 ALSA 设备；
3. 板上现有条件先做最小验证：`arecord -D hw:0,0 -f S16_LE -r 44100 -c 2`（mainline 当前 capture 唯一来源就是 ES7243），若 SDOUT 恒 0xFFFF 则 capture 确实是死的，反过来说明原厂另有链路。

## 4. ~~★ 本轮最实的新线索~~ → 11:13 反汇编核实后撤回

> **⚠ 本节结论已作废，勿再按此改代码。** 11:13 继续反汇编 helper 后，`0x8621` 这条线索被证伪，详见本节末尾「11:13 更正」。采样率 4-bit 码的观察本身仍成立，但它不是 ES7243 寄存器写，归属也未坐实。

vendor `hw_params`（反汇编文件偏移 `0x8427b8`–`0x8428ac`，**归属未坐实，见更正**）把采样率映射成 4-bit 码后统一调用一个 helper：

| 采样率 | 码 | 采样率 | 码 |
|---|---|---|---|
| 44100 | 0 | 32000 | 3 |
| 48000 | 2 | 88200 | 8 |
| 96000 | 0xa | 176400 | 0xc |
| 192000 | 0xe | 其它 | `-EINVAL`（**8k/16k 不支持**） |

```
0x842898: mov w1, #0x8621
0x84289c: mov w2, #0xf
0x8428a0: bl  0x83a1e8     ; helper：x0+0x50 → 0x83a180
```

`0x8621` 超出 ES7243 的 0x00–0x0D 寄存器空间 ⇒ 这次写**不是** ES7243 寄存器，而是经 helper 写到另一个 regmap/对象（推断：时钟或 I2S 控制器侧）。

**mainline 对照**（`kernel-modules/es7243/es7243.c:370-409` `mid_hw_params`）：只做了 `snd_soc_dai_set_bclk_ratio(32*ch)` + 强改 `symmetric_rate`（TRCM_TXONLY）+ `adc_power_up()`；**没有任何按采样率下发 4-bit 码的动作**，也没有 `0x8621` 类写。`mid_set_fmt` 只是打印日志后 `return 0`。

**可执行的下一步**（按性价比）：

1. 反汇编 vendor helper `0x83a1e8` / `0x83a180`，确认 `0x8621` 写到哪个 regmap、位域语义。这是把"推断"变成"可抄数据"的关键一步（本次未做，脚本在 `/tmp/rkrev/`）。
2. 若确认是 I2S/CRU 侧，则在 mainline `mid_hw_params` 里补对应寄存器写；注意 vendor **不支持 8k/16k**，之前用 8k/16k 做的实验本身就不在原厂支持范围内。
3. `0x12` 芯片增益特例（第 7 条 `08=0x21` vs `0x10` 的 `08=0x41`）已有代码级证据，mainline 已实现，无需改。

### ★ 11:13 更正（继续反汇编 helper 后，上述推断作废）

用户「继续做」后反汇编了 helper 链，`0x8621` 线索被证伪：

| 核实项 | 结果 | 证据 |
|---|---|---|
| `0x83a1e8` 函数体 | 只有 `add x0,x0,#0x50` 然后尾调用 `0x83a180`；**不改 w1/w2** | `/tmp/rkrev/disasm.py 0x83a180 0x83a260` |
| `0x83a180` | `x0 ← [x0+0x78]`（ASoC widget/component 对象链），再经 `0x4b34d4` → `0x4b1f38` → `0x4b1d14` | 同上 + 逐层反汇编 |
| `0x4b1d14` | 从 `[obj+0x170]`/`[obj+0x190]` 取函数指针 `blr` —— 典型 **regmap 读改写/update_bits** 框架，不是简单寄存器写 | 反汇编 |
| `0x8621` 全镜像出现次数 | **1 次**，就在 `0x842898`；es7243 代码区 `0x842000-0x846000` 内 0 次作为数据 | `MOVZ w1,#0x8621` 编码 `0x5290c421` 全镜像扫描 |
| `0x8621` 数值 | 34337，远超 ES7243 的 0x00–0x0D 寄存器空间 | 算术 |
| 该函数归属 | `0x8427b8` 引用 `dif-out` DAI 名串（在 `spdif-out`/`dir-hifi` 一带），且紧邻 `snd_tc358749x_dai_hw_params`@`0xbad200` 数据区 ⇒ **很可能是 tc358749x（HDMI 输入）驱动，不是 es7243** | ADRP 页 `0xbad000`/`0xee7000` + rodata |

**结论**：`0x8621` 不是 ES7243 寄存器；这段采样率码即使存在也是走 ASoC widget/regmap 框架的某个对象，既没坐实属于 es7243，也没有可抄到 mainline 的确定寄存器值。**上一轮把它列为「本轮最实线索 / P0」是过度推断，现撤回。** 上面表格里的「可执行下一步」第 1、2 条随之作废；第 3 条（`0x12` 增益特例）不受影响，mainline 已实现。

真正保留的价值只有一条副产品：**vendor 采样率码只覆盖 7 种率、8k/16k 返回 -EINVAL**——提醒后续实验别再用 8k/16k 判断 ES7243（虽然这段归属存疑，但"用受支持的 44.1k/48k 测"本身是合理的谨慎做法）。

## 5. APK 层结论（已挖尽，无后门可抄）

⇒ APK 层到此为止，没有更多线索。
