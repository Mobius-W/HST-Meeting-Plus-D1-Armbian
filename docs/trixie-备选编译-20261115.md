## 三、技术边界：为什么 trixie 不是「引导修复」

引导链由以下四层决定，**没有一层读 `RELEASE`**：

1. BootROM 固定读 eMMC user `LBA64 + 1024n` 找 IDB 魔数 `3b8cdcfc`；
2. `radxa/rk3399-uboot.conf.sh` → `BOOT_SCENARIO=binman-atf-mainline`，U-Boot `tag:v2026.10`，`DDR_BLOB=rk33/rk3399_ddr_933MHz_v1.30.bin`，TF-A `lts-v2.14.11 / PLAT=rk3399`；
3. 单一产物 `u-boot-rockchip.bin`，由 family 官方 `write_uboot_platform()` 一次 `dd bs=32k seek=1` 落到 LBA64（FIT@0x7F8000 → LBA16384）；
4. `armbianEnv.txt` 只换 `fdtfile`（WF7000A 实盘印证，见 `docs/引导机制判定-20261115.md`）。

`RELEASE=trixie|noble` 只改 rootfs：apt 源、`/etc/os-release`、systemd/包版本、`armbian-firmware`、initramfs 内容。`BRANCH=current` 相同 ⇒ 内核包系列（`current-rockchip64`）相同。

⇒ **推论**：路径1 与 trixie 版的「前 16 MiB 引导区」会完全一致（WF7000A trixie 与官方 rockpi4b 已实证零差异）。若失败现象是 BootROM 找不到 IDB / DDR 训练失败 / U-Boot 无输出 / 设备停在 Maskrom，换 trixie **字节级无效**，应回到引导链与板级 DTB/DRAM 方向，不要在这条路上耗时间。

## 四、失败现象 → 是否编 trixie（决策表）

| 观察到的失败点 | 换 trixie 是否有意义 | 应优先查 |
|---|---|---|
| `wl 0` 返回失败 / 读回抽验不一致 | ❌ 无关（写盘层） | USB/OTG、Maskrom vs Loader 坐标、eMMC 写保护 |
| 上电后无 DDR/SPL 输出、USB 仍枚举 rockusb | ❌ 字节级无效 | DDR blob 版本、eMMC boot0/EXT_CSD[179]、BootROM 取盘路径 |
| U-Boot 有输出但 kernel 不启动 / `Starting kernel` 后死 | ⚠️ 弱相关 | 本板 DTB（`rk3399-mid.dtb`）、`fdtfile`、串口 console 参数 |
| kernel 起来、rootfs 挂载/服务异常、包/固件缺失 | ✅ 有意义 | 与 WF7000A trixie 基线对齐后逐项 diff |
| 一切正常，只是想与 WF7000A 保持同发行版 | ✅ 有意义（对齐基线） | 直接编，不改引导链 |
