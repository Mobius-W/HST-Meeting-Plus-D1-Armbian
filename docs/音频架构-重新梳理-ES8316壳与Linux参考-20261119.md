## 0. 结论先行

| 问题 | 一句话答案 |
|---|---|
| **Q1：ES8316 壳为什么能"调用"另外两颗？** | **它根本没有调用。** ES8316 节点在 vendor 里只提供一个 `#sound-dai-cells`（占位 DAI）+ 两个 GPIO，是 ASoC 框架的**接线占位符**；ES7148 是靠 I2S 数据线直接出声的**零控制 DAC**（软件里挂 `es7134` dummy 驱动同理）；ES7243 则**完全不在声卡里**——是独立的 I2C 设备，由 Android HAL/APK 走自己的路径控制。"一个壳调三颗芯片"是伪命题，真实情况是**三条互不相干的线被一个名字掩盖了**。 |
| **Q2：Linux 有成功经验可抄吗？** | **有，但要分芯片。** ES7148 → Linux 标准做法就是 **dummy codec + I2S 三件套**（pcm5102a / simple-card），我们已走通软件层；ES7243 → 上游 2024 年有 **ES7243E 的 ASoC 驱动**（SaluteDevices，源于 Banana Pi R2 Pro BSP），架构可直接参考，但**板上是非 E 版 16 寄存器**，寄存器值不能照搬。真正的新线索是上游 v2 特意补了 **sclk + lrck 两个 clock 输入**，而我们的驱动只接了 MCLK。 |

> **11:27 更新**：§2.3 那条"给 es7243 加 sclk/lrck clock consumer"的 P0 **已撤回**（板上无独立 sclk/lrck clock，见 §6.1）；并且挖到 Android 真 HAL 后，§7 给出了一个更重要的方向修正——**原厂录音走 ALSA capture（I2S0 RX），根本不经 ES7243**，mainline 一直在调错对象。以此处 §7 结论为准。
>
> **11:42 再更正（实测推翻 §7 方向）**：跑了 `arecord` 实测后发现，mainline 的 card0 capture（`mid-audio-hifi`）**恰恰就是我们自己写的 ES7243 驱动**，其 `hw_params` 会对 0x10:00 写 0x01（CSM_ON），因 i2c 无应答（-6）而失败 ⇒ 录音打不开。所以"不经 ES7243、测 I2S0 RX 就行"这个方向**部分作废**——测的还是那条链，只是卡在 ES7243 的 i2c 通信上。以 **§10** 为准。

**★ 本轮最重要的认知翻转**：一直以为"原厂靠 ES8316 驱动管全部音频"。实际上 vendor 内核里 **es7243 没有注册成 ASoC codec**（无 `#sound-dai-cells`、无 `snd_soc_dai_driver`、无 `es7243-hifi` DAI 名），**es8316 驱动也不读任何 I2C 寄存器**。所以原厂音频 = 一个占位 DAI + I2S 数据线喂裸 DAC + 独立 I2C 麦阵驱动。**我们 mainline 把 ES7243 做成 ASoC codec 挂进声卡，这一步在架构上就跟原厂不同**——这未必是错（Linux 主流就该这么做），但它解释了为什么"复刻原厂寄存器"这条路走到头是空的。

## 1. Q1 详解：所谓"ES8316 壳"到底是什么

### 1.1 vendor DTS 的原文（反编译 `rk3399-mid-stock.dts`）

```
i2c@ff110000 {
    es7243@10 { status="okay"; compatible="everest,es7243"; reg=<0x10>; };   // 884-888 行
    es7243@12 { status="okay"; compatible="everest,es7243"; reg=<0x12>; };   // 890-894 行
    es8316@11 {
        #sound-dai-cells = <0x00>;          // ★ 只有它有 DAI 能力
        compatible = "everest,es8316";
        reg = <0x11>;
        clocks = <&cru 0x59>; clock-names = "mclk";
        spk-con-gpio = <&gpio3 0x19 0>;     // GPIO3_C1，喇叭
        amp-en-gpio  = <&gpio3 0x05 0>;     // GPIO3_A5，功放使能
    };
};

es8316-sound {
    simple-audio-card,name = "rockchip,es8316-codec";
    simple-audio-card,cpu   { sound-dai = <0xd8>; };   // i2s0
    simple-audio-card,codec { sound-dai = <0xd9>; };   // ★ 0xd9 = es8316@11，不是 es7243
};
```

**三条硬事实**：
1. `es7243@10/@12` **没有 `#sound-dai-cells`** ⇒ 在 ASoC 框架里根本不能当 codec DAI 用。
2. 声卡的 codec phandle `0xd9` 指向 `es8316@11` ⇒ 整条 ALSA playback/capture 链路只经过 es8316 这一个 DAI。
3. es8316 节点除 DAI 占位外，只有 mclk + 两个 GPIO，**没有任何寄存器配置项**。

### 1.2 vendor kernel.img 字符串证据

| 检查项 | 命中 | 含义 |
|---|---|---|
| `es7243_i2c_probe` / `es7243_init` / `es7243_init_mode` / `es7243_start` / `es7243_startup` / `es7243_set_standby` | 各 1 | es7243 是**独立 I2C 驱动**，函数集是 init/start/standby，不是 codec ops |
| `snd_soc_dai_driver` | **0** | 全镜像没有 ASoC DAI 驱动符号 |
| `es7243-hifi` | **0** | 没有 es7243 的 DAI 名 |
| `Capture MIC Path` / `Playback Path` | **0** | 上一轮已证：这些 HAL 枚举在 kernel+ramdisk 无实现端 |
| `misc_register` / `cdev_init` / `class_create` | 有 | es7243 更可能走杂项字符设备（供 APK/HAL ioctl），而非 ALSA |

### 1.3 所以"调用关系"的真相

```
原厂 Android 音频（三条线，互不隶属）

[播放]  I2S0 ──SDATA/LRCK/SCLK──► ES7148 (裸 DAC，无 I2C，上电即工作) ──► 功放 ──► 喇叭
          ▲
          │ ASoC 需要一个 codec DAI 才能建声卡
          └─ es8316@11 占位 DAI（不读寄存器）+ spk-con/amp-en 两个 GPIO 使能
                    ▲
                    │ Android HAL 下发 Playback Path=SPK
                    └─ vendor "es8316" 驱动收到后拉 GPIO（不是配置 codec）

[录音]  ES7243×2 @ I2C 0x10/0x12 ──独立 I2C 驱动（init/start/standby）──► ?? HAL/APK 自己的路径
        ★ 不在 es8316-sound 声卡里，不产生 /dev/snd/pcmC?D?c，也没有 ASoC DAI

[RTC/灯/云台]  其它独立 misc 驱动（与本问题无关）
```

**回答"是不是厂家惯例/通用封装"**：
- **占位 DAI + GPIO 使能**是 Rockchip vendor BSP 的**惯例做法**（同一个板级模板套不同硬件），不是 ES8316 专用的通用封装。
- 但**不是**"一颗 ES8316 驱动内部同时驱动 ES7148 和 ES7243"——三颗芯片之间没有任何软件调用关系。ES8316 这个**名字**被复用成了"声卡占位符"，仅此而已。
- 这解释了为什么 mainline 真 `es8316.c` 一碰 I2C 0x11 就 210 条 `ASoC error(-6)`（0x11 根本没芯片），也解释了为什么复刻 vendor 寄存器序列一路走空。

## 2. Q2 详解：Linux 侧可抄的参考

### 2.1 ES7148（播放 / DAC）——标准 dummy codec 路线，**我们方向是对的**

**权威参考**：Rockchip 工程师"罗总"《如何编写你自己的 CODEC 驱动》第 2 篇（DAC 播放），2026-08-25，微信公众号原文，已由 Bestom 工程博客规范注解转载：
- https://bestom.net/zh/blog.html
- 规范注解版：https://bestom.net/zh/resources/audio-codec-driver-2-dac-playback.html

核心要点（与我们的现状对照）：

| 参考文章的要点 | 我们的现状 | 是否对齐 |
|---|---|---|
| 零控制 DAC（PCM5102A 类）用 **dummy-codec 占位**，`.playback` 声明只是占位、零行驱动代码 | 板上 `/audio-dac` 绑 `es7134`（`everest,es7144` dummy DAC） | ✅ 对齐 |
| DTS 三件套：Codec DAI（dummy）→ CPU DAI（使能 `&i2s0` + pinctrl）→ Machine（multicodecs/simple card） | card0 `rk3399-mid-es7148` 已注册 | ✅ 对齐 |
| 验证链：`/proc/asound/cards` → `/dev/snd/` → `aplay -D hw:0,0` | PCM RUNNING、MCLK 12.288M、`exit=0` | ✅ 软件层通 |
| ES7148 **没有音量寄存器**，24-bit 全刻度，衰减在软件侧做 | 无需实现 volume 控件 | ✅ 不缺 |
| ES7148 datasheet：MCLK + LRCK 同时到位才离开 power-down | MCLK 有、I2S mailbox 有值；**LRCK/SCLK 波形未实测** | ⚠ 唯一的软件外缺口 |

**结论**：播放侧 Linux 参考已经抄全了，剩下的是模拟侧实测（LRCK/SCLK/SDATA 波形 + VDD + AOUT 共模），不是再找驱动。外部资料也确认 ES7148 "no I²C bus, no register writes, no codec driver to port"（PCB Artists ES7148 Module 产品页）。

### 2.2 ES7243（录音 / ADC）——有上游 ASoC 驱动，但**版本必须分辨**

**上游参考**：
- 补丁：Igor Prusov (SaluteDevices), "[PATCH v2 0/2] Add ES7243E ADC driver", 2024-09-20
  - https://patchwork.ozlabs.org/comment/3383910
  - 源码 693 行 `sound/soc/codecs/es7243e.c`，源于 David Yang 的 Banana Pi R2 Pro BSP 实现：
    https://github.com/BPI-SINOVOIP/BPI-R2PRO-BSP/blob/main/kernel/sound/soc/codecs/es7243e.c

**关键内容**：
- 标准 **ASoC component + DAI** 驱动（`snd_soc_component`、regmap、`init_sequence`），这才是 Linux 主流形态。
- `init_sequence`：CLK2=0x00、SDP=0x00、TDM=0x00、ADC_OSR=0x20（MCLK/LRCK=256）、ADC_VOL=0xbf（0 dB）。
- suspend/resume 用 `ES7243E_PDN=0xff` + CLK1 的 ANA_ON/ADC_ON mask 做电源管理。
- **v2 相对 v1 的关键改动**：`add sclk and lrck clocks`——驱动把 SCLK、LRCK 也 `clk_get`/`clk_disable_unprepare`，即 **ES7243 需要三路时钟输入，不只是 MCLK**。

**版本红线（已有文档钉死，重申）**：
- 板上是 **ES7243（16 寄存器，非 E 版）**；ES7243E 的寄存器表完全不同（0x03 默认 0x20、0x09 默认 0xC1；E 版有 0x10–0x18 ANALOG 寄存器，非 E 版没有）。**ES7243E 的 init_sequence 数值不能照搬。**
- 判据：`docs/麦阵-ES7243-MCLK破案与软件侧穷尽-20261117.md` §二；CHIP_ID `0xFD=0x60`/`0xFE=0x40` 是 0x0D 的镜像，不是 E 版的 `0x7A/0x43`。

**可抄 vs 不可抄**：

| 项 | 能否抄 | 说明 |
|---|---|---|
| 驱动形态（ASoC component/DAI、regmap、DAPM） | ✅ 能，架构层面 | 我们已经是这个形态，方向正确 |
| **SCLK + LRCK 也作为 clock 输入** | ⚠ **值得核对** | 上游 v2 专门补这一条；我们的 `es7243.c` 只有 `mclk_clk`（`devm_clk_get(...,"mclk")`，12288000 Hz），**没有 sclk/lrck clock consumer**。时序上 ES7243 需要 LRCK/SCLK 边沿才能推进状态机，而我们的 SDOUT 恒 `0xFFFF`、`0x0D` 恒 `0x60`。这是目前**唯一没试过的时钟维度**。 |
| 寄存器值（ADC_OSR=0x20 等） | ❌ 不能抄 | 非 E 版寄存器表不同 |
| PDN/CLK1 电源管理位 | ❌ 不能直接抄 | 非 E 版无对应寄存器；但"需要显式 power-up/down 序列"的**思路**可借鉴 |

### 2.3 一条新的可执行线索（P0）

上游 v2 补 `sclk`/`lrck` clock 这一条，和我们的症状高度吻合：

- 症状：`SDOUT` 恒 `0xFFFF`，`0x0D CHIP STATE` 恒 `0x60`（默认 0xA0，bit7=0）——**芯片状态机不推进**。
- 我们已排除：MCLK（12.288M 常开）、I2C（全通）、寄存器序列（vendor 11 写逐字节一致）、采样率（8k/16k/48k）、声道数、bclk_ratio、TRCM。
- **未试过**：让 ES7243 驱动显式获取并 enable **lrck（SCLK_I2S0_8CH 的 frame clock）与 sclk（bit clock）** 作为 consumer，而不是只靠 SoC I2S 控制器自己在 playback 时才输出时钟。若 ES7243 需要这两个时钟在 I2C 初始化前就稳定，我们现在的 `capture-only` 场景下 I2S0 可能根本没被 clock on ⇒ 芯片永远等不到 LRCK ⇒ SDOUT 不推进。
- 做法（静态可先做）：照上游 binding 给 `es7243@10/@12` 加 `clocks = <&cru SCLK_I2S0_8CH>, <&cru ...>`, `clock-names = "sclk","lrck"`（具体 clock 名需查 CRU），驱动里 `devm_clk_get` + `clk_prepare_enable`，时序放在 `es7243_init` 之前。

⚠ 注意：非 E 版 datasheet 未必显式要求 sclk/lrck 作为输入 clock；这是**跨版本的结构性推测**，不是已证事实。价值在于它是软件侧**最后一个没试过的维度**，且上游驱动的行为给了合理性支撑。

## 6. 静态核对结果（11:27，板上 `10.26.88.10` 实时）

### 6.1 I2S0 时钟树（`clk_summary` 实测）

```
clk_i2s0_div     1  800000000  Y
  └ clk_i2s0_frac 1  12288000   Y
      └ clk_i2s0_mux 1 12288000  Y
          └ clk_i2s0  1  12288000  Y
                consumers: mic-array (我们的 es7243 驱动)
                           i2s@ff880000 (CPU DAI, i2s_clk)
hclk_i2s0        1  100000000  Y   consumer: ff880000.i2s
clk_i2sout_src   0  12288000   Y   (未 enable)
  └ clk_i2sout   0  12288000   N
```

**结论**：
- MCLK = **12.288 MHz 已确认**，且 `clk_i2s0` 同时被 `mic-array` 和 I2S0 控制器持有（prepare/enable count=1，ref=2）——上一轮"MCLK 常开、consumer 显示 mic-array"属实。
- **板上没有独立的 sclk/lrck clock 节点**：RK3399 I2S 的 bit/frame clock 由 `clk_i2s0` 在 I2S 控制器内部按 `bclk_ratio` 分频产生，不像 ES7243E 上游驱动那样可以从 DT 拿到独立 `sclk`/`lrck` clock。⇒ **§2.3 那条"给 es7243 加 sclk/lrck clock consumer"的 P0 建议，在这块板上无对应 clock 可加，判定不可执行、撤回。** 上游 ES7243E 的时钟接线SoC 平台相关（BPI-R2 Pro 的 feed 方式不同），不能照搬概念。
- §2.3 的诊断价值保留：它提示"LRCK/SCLK 边沿是否稳定"仍值得查，但手段改为**实测波形/寄存器**，不是加 clock consumer。

### 6.2 声卡与 PCM 节点（实测）

```
card0: rk3399mides7148 (simple-card)   → pcmC0D0p + pcmC0D0c 都在
card1: hdmisound                       → pcmC1D0p + pcmC1D0c
```

- **`pcmC0D0c` 已存在**（capture 节点早在），说明 ASoC 声卡 bind 没问题，问题在 codec/数据侧。
- 这支持 §2.1 的判断：播放侧软件链路已通，录音侧缺的是芯片真正输出数据。

### 6.3 撤回与保留（对 §2.3 / §4 的更新）

| 项 | 处理 |
|---|---|

## 7. Android 到底怎么调用音频输入/输出（11:27 挖到底）

### 7.1 真正的 Audio HAL 在哪（差点被骗）

| 文件 | 大小 | 真伪 |
|---|---|---|
| `/system/lib/hw/audio.primary.default.so` | 18 KB | ❌ AOSP 通用 stub（导出符号只有 `__aeabi_*`、无 `adev_open`），不是本板实现 |
| `/system/vendor/lib/hw/audio.primary.rk30board.so` | **126 KB** | ✅ **真正的 Rockchip HAL**（此前一直漏了 `vendor/` 子目录） |
| `librk_audio.so` | 858 KB | ❌ 是 AAC/WMA/DTS/AC3 **解码库**，不是 HAL |
| `libaudioroute.so` | 22 KB | ✅ mixer 路径应用库（`audio_route_apply_path` 等） |

### 7.2 HAL 的输出调用链（喇叭出声）

```
App (MediaPlayer/AudioTrack)
  → AudioFlinger
    → audio.primary.rk30board.so  adev_open_output_stream()
      → 读 /proc/asound/card0/id 得到声卡 ID       [strings: 0x112aa/0x112c0]
      → sound_card_config_list 按 ID 查配置表        [symbol @0x25200]
      → 若 ID == "rockchipes8316c" → 选 es8316_config_table (全套 es8316_*_controls)
      → 解析 mixer_paths.xml: path "speaker" → ctl "Playback Path"="SPK"
      → audio_route_apply_path() → mixer_open("/dev/snd/controlC%d") 下发控件
      → vendor es8316 驱动收到 SPK → 拉 spk-con/amp-en 两个 GPIO（功放开）
      → tinyalsa pcm_open(PCM_CARD, 0, OUT) → pcm_write() → I2S0 → ES7148 裸 DAC → 喇叭
```

**★ 这就是"安卓一直用 ES8316"的真相**：HAL **只看 `/proc/asound/card0/id` 的字符串**去 `sound_card_config_list` 查表，匹配 `rockchipes8316c` 就套用 es8316 全套控件——**与板上真实是否有 ES8316 芯片无关**。vendor DTS 的 `simple-audio-card,name="rockchip,es8316-codec"` 让声卡 ID 正好叫这个名字，于是 HAL 一路按 es8316 走。所谓"用 ES8316"是**字符串层面的配置查表**，不是真的在操作 ES8316 硬件。

### 7.3 HAL 的输入调用链（录音）

```
App (AudioRecord / MediaRecorder, AudioSource=MIC)
  → AudioFlinger
    → audio.primary.rk30board.so  adev_open_input_stream()
      → 同样按声卡 ID 查表 → es8316_config_table
      → mixer_paths.xml: 所有 capture path（main-mic/second-mic/headset-mic）
          统统 → ctl "Capture MIC Path"="Main Mic"      ← 关键：四路都指向同一个枚举
      → vendor es8316 驱动收到 "Main Mic" → 配置模拟输入路由
      → tinyalsa pcm_open(PCM_CARD, 0, IN) → pcm_read() → ALSA capture
```

**关键证据**：
- `mixer_paths.xml` 里 `media-second-mic`、`media-headset-mic`、`voice-rec-main-mic` **全部复用 `main-mic` 这一个 path**，只下发 `Capture MIC Path=Main Mic` 一个枚举。
- **`audio.primary.rk30board.so` 全库零命中 `es7243`/`mic-array`**；控制表只有 es8316/es8396/cx2072/rt56xx/wm8960 等**标准 codec 模板**，没有麦阵专用路径。

**⇒ Android 录音根本不经过 ES7243。** HAL 走的是 es8316 空壳 DAI 后面的 **ALSA capture 节点**（I2S0 的 RX 方向），即 std `pcmC0D0c`。所谓"4 麦阵列"的波束/DOA 是 `libRealAudio.so` 在**拿到 PCM 之后**做的软件算法（APK 报告已证：纯软件、只 import `fopen`、不碰 I2C）。ES7243×2 是**另一条独立 I2C 设备线**，Android 标准录音链路不用它——这与 §1 的"三条线互不隶属"完全自洽。

### 7.4 对 mainline 的最终指导

| 现象 | Android 真相 | mainline 该怎么做 |
|---|---|---|
| 喇叭能响 | HAL 按声卡 ID 套 es8316 控件表 → 拉 GPIO → I2S 喂 ES7148 | 我们 dummy codec + 功放 GPIO 已等价；缺的是模拟侧实测（§2.1） |
| 麦克风能录 | HAL 走 **ALSA capture（I2S0 RX）**，控件只是 `Capture MIC Path=Main Mic` 枚举，**不经 ES7243** | ⚠ **我们方向可能错了**：一直在调 ES7243 寄存器/SDOUT，但原厂录音压根不走它。应先验证 `pcmC0D0c`（I2S0 capture）本身能不能收到数据——这才是与原厂等价的路径 |
| ES7243×2 存在 | 独立 I2C 设备，Android 标准录音不用；可能供特定 APK 走私有路径或作它用 | 不必强求把它做成主 capture codec；先确认 `pcmC0D0c` 是否能通 |

**★ 最重要的可执行结论**：最小验证要从"调 ES7243"转向 **`arecord -D hw:0,0 -f S16_LE -r 44100 -c 2` 测 card0 的 capture（I2S0 RX）**。这和 Android 实际录音路径等价。如果这条能收到数据，麦阵问题就根本不在 ES7243；如果收不到，再回头查 I2S0 RX 的时钟/引脚，也不是 ES7243 寄存器。

### 7.5 证据定位

- 真 HAL：`/mnt/stock/vendor/lib/hw/audio.primary.rk30board.so`（板上），本地副本 `/tmp/audio-hunt/stock/`
- 声卡 ID 查表：HAL 字符串 `@0x126ee` = `rockchipes8316c`、`@0x126af..0x12711` = ID 表；symbol `sound_card_config_list@0x25200`、`es8316_config_table@0x244b0`

- APK 侧：`libRealAudio.so` 纯软件算法，不碰硬件（见《音频麦阵-测试APK调用链-20261119.md》C4）

## 8. ★ "ES8316 兼容框架"拆解（11:33，用户命题：把里面所有兼容型号拆出来）

### 8.1 HAL 层：12 个型号配置表塞在同一个 `audio.primary.rk30board.so`

`strings audio.primary.rk30board.so | grep -oE '^[a-z0-9_]+_config_table$'` 得到完整型号清单：

| # | config_table | # | config_table |
|---|---|---|---|
| 1 | `cx2072_config_table` | 7 | `rt3224_config_table` |
| 2 | `default_config_table` | 8 | `rt3261_config_table` |
| 3 | **`es8316_config_table`** ← 本板命中 | 9 | `rt5616_config_table` |
| 4 | `es8396_config_table` | 10 | `rt5640_config_table` |
| 5 | `hdmi_analog_config_table` | 11 | `rt5651_config_table` |
| 6 | `rk616_config_table` | 12 | `wm8960_config_table` |

每个表都有完整的一套场景控件（incall/ringtone/voip/normal × speaker/headphone/headset/earpiece/bluetooth + capture + off），例如 `es8316` 一家就有 24 个 `es8316_*_controls` 子表。HAL 启动时读 `/proc/asound/card{0,1,2}/id`，在 `sound_card_config_list` 里按**声卡 ID 字符串**查表——这是纯软件路由，**和板上实际有没有这颗芯片无关**。

### 8.2 kernel 层：同一驱动 rodata 里混编了 4 家芯片的控件表

vendor kernel.img `0xee5c80..0xee64ff` 一段 rodata 里同时出现：

|---|---|---|
| **ES8316** | `es8316`(0xee60b1)、`ES8316 HiFi`(0xee60b8)、`Differential Mux`(0xee60d1)、`lin1-rin1`(0xee60e2)、`ALC Capture Function`(0xee6444) 等**完整标准 ES8316 控件表** | 模板主体 |

### 8.3 "路径控件"是 HAL 虚构的，kernel 里根本不存在（交叉验证表）

| 控件名 | HAL | vendor kernel | 结论 |
|---|---|---|---|
| `Playback Path` | 1 | **0** | HAL 自有枚举，不下发内核 |
| `Capture MIC Path` | 1 | **0** | HAL 自有枚举，不下发内核 |
| `Main Mic` | 3 | **0** | HAL 自有枚举 |
| `SPK GPIO Control` / `HP GPIO Control` / `RCV GPIO Control` | 有 | **0** | HAL 虚拟控件，内部映射到底层操作 |
| `Differential Mux` | 1 | 1 | 真实 ASoC 控件，HAL↔kernel 都有 |
| `lin1-rin1` | 0 | 2 | 真实控件（kernel 侧） |
| `Headphone Playback Switch` | 1 | 1 | 真实控件 |

HAL 的全部 path 枚举（`@0x1141e` 起）：
- `Playback Path` = SPK / RING_SPK / SPK_HP / RING_SPK_HP / HP_NO_MIC / RING_HP_NO_MIC / RING_HP / RCV / Voip Path / Voice Call Path
- `Capture MIC Path` = Main Mic / Hands Free Mic / BT Sco Mic / MIC OFF / OFF
- 离散 GPIO 控件 = `SPK GPIO Control` / `HP GPIO Control` / `RCV GPIO Control`（值 High/Low）

**这彻底作废了旧结论**："mainline 丢了 Playback Path/Capture MIC Path 控件导致无声"——这些控件从来不在内核里，是 HAL 为了统一上层接口造的软件枚举，HAL 把它翻译成真实 mixer 写 + GPIO 操作。mainline 不需要复刻它们。

### 8.4 物理层验证（板上 `10.26.88.10` 实测，11:33）

| 检查 | 结果 |
|---|---|
| `i2cdetect -y -r 1` | i2c-1 **全空**——0x10/0x11/0x12 全部 `--` |
| `i2cget -y 1 0x11 0x00` | `Error: Read failed` ⇒ **物理上不存在 ES8316@0x11** |
| `/sys/bus/i2c/devices/` | 只有 `1-0010`/`1-0012`（mainline ES7243 占用），无 `1-0011` |
| 板上声卡 | card0=`rk3399mides7148`、card1=`hdmisound`——**没有 `rockchipes8316c`** |
| 控件数 | `amixer -c 0 scontrols` = 0（dummy codec 无控件，符合预期） |

⇒ **Android 挂的 ES8316 驱动 probe 面对的是一个不存在的 I2C 芯片**。这就是"空壳"的真相：它不靠 I2C 寄存器出声，靠 (a) simple-audio-card 声卡模板占位 + (b) DTS 的 spk-con/amp-en 两个 GPIO 控制功放 + (c) ES7148 裸 DAC 直接吃 I2S 数据。ES8316 的整套寄存器控件表只是被编进内核但从未被真实使用（或 probe 失败/容错跳过）——纯模板残留。

### 8.5 对 mainline 的最终指导（命题的答案）

用户"拆出所有兼容型号"的命题**成立且有实际价值**，但价值不在于"复刻某个型号的寄存器"：

1. **不要复刻 ES8316 控件表**。板上没有这颗芯片，那些 `Differential Mux`/`ALC Capture` 控件对 ES7148（无寄存器）毫无意义。我们把 ES7148 做成 dummy codec 是**正确且与厂商壳等价**的做法。
2. **出声的唯一硬件动作 = I2S0 数据 + 功放 GPIO**。vendor 靠 `spk-con`(GPIO3_25)/`amp-en`(GPIO3_5) 拉功放；mainline 若无声，先查这两个 GPIO 在 mainline 是否已导出/拉高，再查 I2S0 TX 波形——不是查 codec 寄存器。
3. **录音不经过任何 codec 寄存器路径**：HAL 的 `Capture MIC Path=Main Mic` 是软件枚举，实际走 ALSA capture（I2S0 RX）。4 麦波束是 APK 层 `libRealAudio.so` 对 PCM 的软件算法。⇒ 验证方向仍是 `arecord -D hw:0,0 -f S16_LE -r 44100 -c 2` 测 I2S0 RX。
4. **ES8316/ES7243/CX2072X 混编是 Rockchip BSP 通用做法**，不是本板特例；`es8316` 这个名字是**声卡模板 ID**，不是硬件事实。以后看 Rockchip 板子音频，一律先查 `/proc/asound/card0/id` + HAL 查表，别被驱动名误导。

## 10. ★ 实测线索测试 + "8316 万能驱动"的精确回答（11:42）

用户两问：①按挖出的线索实测；②既然没有 8316 硬件，Android 是不是把 ES7XXX 驱动写进 8316 驱动里、8316 是个能兼容 N 型号的万能驱动？逻辑是什么、Linux 能抄多少？

### 10.1 实测：`arecord` 录音直接失败，根因是 ES7243 i2c 无应答

按 §7 结论测 `arecord -D hw:0,0 -f S16_LE -r 44100/48000 -c 2`：

| 项 | 结果 |
|---|---|
| capture 设备 | card0 `rk3399mides7148` device0 = `ff880000.i2s-mid-audio-hifi` |
| 44100 | `Unable to install hw params`（period 参数不匹配） |
| 48000 + 固定 period | 命令 rc=0 但**未生成 wav 文件** |
| **dmesg 根因** | `rk3399-mid-audio mic-array: i2c write 10:00=01 failed (-6)` → `ASoC error (-6) at snd_soc_dai_hw_params()` on mid-audio-hifi |
| 源码对应 | `kernel-modules/es7243/es7243.c:370 mid_hw_params` → `adc_power_up()` → `adc_write(0x10, 0x00, 0x01)`（CSM_ON）；`es7243.c:171 dev_err("i2c write...failed")` |

**★ 这推翻了 §7 的方向结论**：mainline 的 card0 capture **就是**我们自己写的 ES7243 ASoC codec，录音链完全依赖它。§7 说"测 I2S0 RX 不经 ES7243"是错的——测的就是经 ES7243 的链，只是卡在 i2c 通信。

### 10.2 i2c 无应答的性质（硬件层，独立于架构问题）

| 检查 | 结果 |
|---|---|
| `i2cdetect -y -r 1`（多次） | i2c-1 **全空**，0x10/0x12/0x11 全部 `--` |
| `i2cget 1 0x11 0x00` | Read failed |
| `/sys/bus/i2c/devices/1-0010`/`1-0012` | 存在，modalias=`everest,es7243`，of_node status=`okay`，但无有效 driver symlink |
| 真实驱动名 | `rk3399-mid-audio`（platform driver），不是 `es7243` |
| i2c-1 时钟 | `clk_i2c1` = 200 MHz，正常 |
| 对照 i2c-6 | 氛围灯 0x50/0x52/0x53 同晚可正常通信 ⇒ i2c 子系统本身好，i2c-1 这条总线/ES7243 供电有问题 |

⇒ 这是**独立的硬件/供电问题**（记忆里"ES7243 i2c 全通"是旧状态，现已失效）。注意：旧记忆明确警告过"删 avdd supply 回 dummy"方向已被证伪，不要重走；要查只能实测供电/LDO 是否真到 ES7243 avdd 脚。

### 10.3 "8316 万能驱动"的精确回答（用户命题：部分成立，但要拆成两层）

用户的直觉对了一半，但把两个层次混在了一起。**必须区分 HAL 层与 kernel 层**：

| 层次 | "8316" 是什么 | 是不是万能驱动 |
|---|---|---|
| **Android HAL 层** | `es8316_config_table` + 24 个 `es8316_*_controls` 子表，按声卡 ID 字符串查表 | **✅ 是**——这是真正的"万能框架"：12 个型号表（cx2072/es8316/es8396/rk616/rt3224/rt3261/rt5616/rt5640/rt5651/wm8960/hdmi_analog/default）塞在一个 so 里，用同一套虚拟控件名（`Playback Path`/`Capture MIC Path`/`SPK GPIO Control`...）屏蔽硬件差异 |
| **vendor kernel 层** | `es8316` 是一个**标准的 ES8316 ASoC codec 驱动**（完整寄存器控件表：`Differential Mux`/`lin1-rin1`/`ALC Capture Function`/`Left Hp mux`...，i2c id 表 + `10ES8316:00` ACPI HID） | **❌ 不是万能驱动**——它就是 ES8316 本身的代码。ES7XXX 的驱动**没有**被写进 8316 驱动里 |

**所以准确的机制是**：

1. **"万能"在 HAL，不在驱动**。Android 之所以能"用 8316 名字驱动非 8316 硬件"，是因为 HAL 的 `sound_card_config_list` 按声卡 ID 查到 `es8316_config_table`，这套表用的是**虚构的路径控件**（`Playback Path`/`SPK GPIO Control` 等，kernel 里 0 命中），HAL 把它们翻译成底层动作。**硬件差异被 HAL 的字符串表 + 虚拟控件屏蔽了，不是被驱动代码屏蔽的**。
2. **ES7148（裸 DAC 无 I2C）根本不需要"驱动"**——它没有寄存器可写。所谓出声 = simple-card 占位 DAI + I2S 数据线 + DTS 两个 GPIO（spk-con/amp-en）拉功放。8316 的寄存器表在这里是**死代码**。
3. **ES7243 有自己独立的驱动**（`es7243_i2c_probe`/`init_mode`/`startup`/`set_standby`，kernel rodata `0xbad3e0`），**没有被塞进 8316**。它是 i2c 设备，不是 ASoC codec，不在声卡里。
4. **CX2072X / dw-hdmi / bt-sco 的控件表和 es8316 编在同一段 rodata**，这是**编译单元布局**，不是"一个驱动兼容多家"——它们是各自独立的驱动，只是 .rodata 被链接器放在一起。

**一句话**：不是"8316 驱动兼容 N 个型号"，而是"**一套 HAL 配置表 + 虚拟控件名兼容 N 个型号，kernel 里每家仍是各自的驱动；而这颗板上连 8316 芯片都没有，8316 只是声卡模板名**"。

### 10.4 Linux 能抄多少（可执行结论）

| 能抄的 | 不能抄/不必抄的 |
|---|---|
| ✅ **ES7148 = dummy codec + I2S 三件套**：我们已做，且与厂商壳**等价**（都是占位 DAI + I2S 数据） | ❌ ES8316 的完整寄存器控件表——板上无此芯片，死代码，抄了无用 |
| ✅ **功放 GPIO 机制**：出声靠 spk-con(GPIO3_25)/amp-en(GPIO3_5) 拉高，mainline 要确认这两个 GPIO 已导出并拉高 | ❌ HAL 的 `es8316_config_table` / 虚拟路径控件——那是 Android audio HAL 概念，Linux 无对应物 |
| ✅ **ES7243 独立 i2c 驱动思路**：作为 i2c 设备操作，寄存器序列 vendor/mainline 已一致 | ❌ "把 ES7XXX 写进 8316"——这个前提不成立，没有这种代码可抄 |
| ⚠️ 上游 ES7243E ASoC 驱动（`patchwork 3383910`）架构可参考，但非 E 版寄存器不可照搬 | — |

**★ 当前真正的卡点（从架构转到硬件实测）**：录音链打不开不是驱动逻辑问题，是 **ES7243 在 i2c-1 上物理无应答**（-ENXIO）。软件侧（寄存器序列、时钟、控件）已穷尽，下一步只能实测：ES7243 的 avdd/vdd 供电是否到位、i2c-1 总线（SDA/SCL）是否正常、芯片是否损坏。不要再改 DTS 文本或驱动代码猜。

### 11.3 对卡点的收敛：优先查「共享条件」，不是单颗芯片

`i2cdetect -y -r 1` 是**两颗 ES7243 同时全空**（i2c-6 三颗 LED 驱动同时正常）。两颗芯片同时失效的概率低于共享条件失效 ⇒ 按手册给出的先决条件排序实测：

| 序 | 量测点（需万用表/示波器，软件查不到） | 判据 |
|---|---|---|
| 1 | ES7243 **pin 1 VDDP** 直流电压 | 应为 1.8 V 或 3.3 V；为 0 ⇒ I2C 数字域没供电，全空必然 |
| 2 | i2c1 SDA/SCL 空闲上拉电压 | 必须与 VDDP 同域；3.3 V 上拉 + 1.8 V VDDP = 超绝对最大；1.8 V 上拉 + 3.3 V VDDP = 达不到 VIH |
| 3 | ES7243 **pin 20 MCLK** 波形 | 12.288 MHz、占空比 40–60 %（软件已证时钟开，引脚实测补最后一段） |
| 4 | **pin 17 AD0 = 0**；**pin 8 AD1** = 0（0x10）/ 1（0x12） | 与 DTS 写死地址一致；不一致则实际地址落在 0x11/0x13 |

> 若 1/2 不匹配 ⇒ 板级电平域问题，改上拉/供电，不是改驱动；若 1–4 全部匹配仍全空 ⇒ 才轮到 i2c1 总线物理层（断线/ESD）。**全程不刷机、不改 DTS 猜、不预设芯片损坏**——与用户 11-19 的要求一致。

## 12. ★ 根因锁定：MCLK 时钟选错（0x56 → 0x59），i2c-1 全空的软件层解释（12:1x）

> 触发：§11 手册确认「ES7243 的 I2C/状态机依赖 MCLK」，回头复核 11-19 日志 §末「clock index 0x59 vs mainline SCLK_I2S0_8CH 是否同一路未核实」这唯一遗留点。**结论：不是硬件坏，是 mainline DTS 把 MCLK clock 选错了。全程只读上板核对 + 本地静态核对，未刷机。**

### 12.1 证据链（本地静态 + 板上只读，逐条可定位）

| # | 证据 | 结论 |
|---|---|---|
| 1 | `wf7000a/wf7000a-dtb/upstream-6.18/include/dt-bindings/clock/rk3399-cru.h:46`：`#define SCLK_I2S_8CH_OUT 89`；项目 `tools/patch-dtb-micarray.py:71` 注释 `SCLK_I2S0_8CH = 86` | **0x59(89) 与 0x56(86) 是两路不同的 clock**，此前日志的「未核实」现在判明 |
| 2 | vendor `rk3399-mid-stock.dts:2886`：`i2s-8ch-mclk { rockchip,pins = <0x04 0x00 0x01 0xbc>; }` = **GPIO4_A0 func1**；原厂 es8316@11 `clocks=<&cru 0x59>` | 原厂 MCLK 走 0x59 → GPIO4_A0，送到外部 codec |
| 3 | upstream `rk3399-rock-pi-4.dtsi:477`：es8316 `clocks = <&cru SCLK_I2S_8CH_OUT>` | mainline 标准板同样用 0x59，本板改成 0x56 是**偏离上游** |
| 4 | 本板 DTS 原 `rk3399-mid.dts:207`：`mic_array clocks = <&cru SCLK_I2S0_8CH>`（0x56） | 错在这里：0x56 是 I2S 控制器内部时钟，**不上 MCLK 脚** |

| 8 | 本轮复核 `i2cdetect -y -r 1` 仍**全空**；板子 uptime 3 min（11:5x 软复位后已恢复） | 现象稳定，不是操作假象 |

### 12.2 因果链

```
DTS 把 mic-array 的 mclk 写成 SCLK_I2S0_8CH(0x56)
  → 驱动 prepare_enable 的是 clk_i2s0，不是 clk_i2sout
  → clk_i2sout(0x59) 全程 N，GPIO4_A0 无 MCLK 波形
  → ES7243 pin20 无 MCLK（§11.1 手册先决条件不满足）
  → 芯片时钟管理/状态机不工作 → I2C 无应答 (-ENXIO)
  → i2c-1 两颗同时全空 → arecord hw_params 写 0x10:00=01 失败
```

**这同时解释了三个旧谜团**：① 两颗 ES7243 同时失效（共享 MCLK，非两颗同时坏）；② i2c-6 氛围灯正常（LED 驱动不需 MCLK）；③ 软件看到「MCLK 12.288M 常开」却芯片不应答（看的是 `clk_i2s0`，不是真正上脚的 `clk_i2sout`）。

### 12.5 ES7148 播放侧复核（12:1x，用户：「音频呢？ES7148 手册也给你了」）

用户追问录音通了、播放（ES7148）如何。**结论（已实测闭环）：本次 `clk_i2sout` 0x56→0x59 的修复同时补上了 ES7148 一直缺的那路引脚级 MCLK，喇叭已真实出声。** ES7148 是纯模拟 DAC（无 I2C/无寄存器），软件侧无法自证出声，最终判据是用户耳朵——板上播放 1kHz 测试音后用户确认「有声音啊」⇒ 播放链打通，与录音同为「一个 clock cell」根因。至此音频（录 + 放）整体闭环。

**为什么这次修复对播放也关键**（对照 ES7148 DS Rev11 §3）：

| ES7148 手册要求 | 修复前 | 修复后 |
|---|---|---|
| 上电进入 power-down，输出钳地；**须 CLKIN 与 LRCK 同时有效**才离开、输出从地软启到共模 | 旧记录 `硬件清单:121/701`：播放「软件链路 100% 通、`clk_i2s0` 12.288M、FIFOLR=0x15、功放 GPIO hi，但用户听无声」——当时 `clk_i2sout`=N ⇒ **引脚级 MCLK 从未输出到 ES7148 pin3 CLKIN** | `clk_i2sout`=Y（12.288M，mic-array 持有常开）⇒ GPIO4_A0 有 MCLK 波形，与 LRCK 同时到位 ⇒ 满足手册离开 power-down 的先决条件 |
| CLKIN/LRCK=256（48k→12.288M） | 频率对但没到引脚 | ✅ 12.288M/48k=256，落在手册 Table 1 single-speed 档 |

**播放链软件前提全绿（实测）**：播放中 pinmux 从 `i2s0-8ch-bus-bclk-off` → `i2s0-8ch-bus`（pin120/121/128 全切到有 clock 的组，LRCK/SCLK/MCLK 上脚）；功放 `amp-en`(gpio5)=out hi、`spk-con`(gpio25)=out hi；`aplay -D hw:0,0 /tmp/tone1k.wav` rc=0、PCM RUNNING；`clk_i2s0`/`clk_i2sout` 均 12.288M/Y；播放链未动（card0 es7148 + card1 hdmi 正常）。

**与 ES7243 的关系（已闭环）**：两颗音频芯片共用 GPIO4_A0 这一路 MCLK（原厂一路 MCLK 供所有 codec）——由"改同一个 clock cell 后 ES7243 I2C 恢复 + ES7148 出声"双向实证。录音、播放同根同源、同一次修复解决。**最终判据**：板上 `aplay /tmp/tone1k.wav`（1kHz/48k/2ch）后用户确认听到声音 ⇒ ES7148 拿到 CLKIN+LRCK 后正常退出 power-down 出声，播放链闭环。音频全链路（mic 录 +喇叭 放）至此全部打通，无需任何硬件模拟侧量测。

**★ 最终判词**：卡了几天的「音频+麦阵」大问题，根因就是 DTS 里 mic-array 的 **1 个 clock cell**（0x56→0x59，`SCLK_I2S0_8CH`→`SCLK_I2S_8CH_OUT`）。一个字节的 DTB 改动同时修复了录音（ES7243×2 I2C 无应答）与播放（ES7148 引脚级 MCLK 缺失）。硬件全程完好——再次印证用户"不猜硬件坏、在 Armbian 上找"的判断正确。
