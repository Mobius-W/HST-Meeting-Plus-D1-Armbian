# 引导机制判定：Armbian 与 Android 引导是否有关（rk3399-mid）

> 判定日期：2026-11-15 22:0x
> 触发问题：WF7000A 首次刷 Armbian 时初始系统是 Android 7，用的是 rockpi4b 固件 +
> `rk3399_loader_v1.30.130.bin`，没有参照任何 Android 引导 ⇒ 后续编译究竟以
> **armbian 官方引导方式**为主，还是以**板子原厂（vendor/Android）引导**为主？
> 方法：对 rockpi4b / WF7000A / WF7000A 原厂安卓 / mid 原厂安卓 / ophub 新参照 /
> 本项目 CI 产物做**扇区级 + 逐字节**比对；armbian 官方源码交叉验证。

---

## 〇、结论先行

1. **Armbian（官方 mainline 链）的引导与 Android 引导无关。**
   两者唯一交集是 **SoC 固化的 BootROM 行为**：上电后去 eMMC user area 的
   `LBA64 + 1024n` 槽找 IDB 魔数 `3b8cdcfc`。Android 只留下一个**物理状态**
   （eMMC 未启用硬件 boot 分区 ⇒ BootROM 走 user LBA64），
   **不留下任何被 Armbian 读取的引导内容**。
2. **编译应以 armbian 官方引导方式为主，不应以板子原厂为主。**
   原厂 `parameter` / `mtdparts` / `LOADER@8192` / `BL3X@16384` / `RSCE@32768`
   是 vendor miniloader 链的私有约定；一旦 LBA64 换成 mainline IDB，
   整条 vendor 链被绕过，写在那里的东西是**死数据**。
3. **三份 Armbian 的引导方式并不一致，分三派**（详见 §二）：
   官方派（rockpi4b ≡ WF7000A）、ophub 混搭派（AIO-3399C）、
   本项目当前派（vendor only-blobs + 缺 IDB）。
   ⇒ **ophub 参照在引导链上更远，不是基线的正确来源**；它的价值在硬件适配参考，不在引导。
4. **刚触发的 `run 43720388847` 仍是「以板子原厂为主」的方向**，按本判定应切换基线。

### 1.4 armbian 官方源码交叉验证

`config/sources/families/include/rockchip64_common.inc`：

| 位置 | 内容 |
|---|---|
| :132-134 | `rk3399)` 分支默认 `BOOT_SCENARIO="only-blobs"`、`DDR_BLOB=rk33/rk3399_ddr_933MHz_v1.25.bin` |
| :364-383 | **`write_uboot_platform()` 按产物文件分派**：`u-boot-rockchip.bin` → `bs=32k seek=1`（=LBA64，内含 IDB+FIT）；`u-boot.itb` → `idbloader.img@64` + `u-boot.itb@16384`；`uboot.img` → only-blobs 的 `64/16384/24576` |
| radxa `config/sources/vendors/radxa/rk3399-uboot.conf.sh:9` | **`BOOT_SCENARIO="binman-atf-mainline"`**（mainline U-Boot + mainline TF-A + Rockchip DDR blob 作 TPL） |

⇒ rockpi4b 走 mainline 链**不是靠手写坐标**，而是靠

**「以官方引导方式为主」= 用官方 scenario / 产物分派，不自定义坐标 hook。**

## 二、三派引导方式对照

| | 官方 mainline 派 | ophub 混搭派 | 本项目当前 |
|---|---|---|---|
| 代表 | rockpi4b ≡ WF7000A | r432 AIO-3399C | `rk3399-mid.csc`（run 43720388847） |
| 首级 | `u-boot-rockchip.bin` @LBA64（IDB `3b8cdcfc`） | IDB @LBA64 | **LBA64 全零**（20:2x 修复中补 IDB） |
| 二级 | FIT `d00dfeed` @LBA16384（含在首级文件内） | `LOADER` @16384 | `LOADER` @8192 |
| 三级 | 无（ATF 编进 FIT） | `BL3X ec000300` @24576 | `BL3X ec000300` @16384 |
| 分区 | MBR + ext4 `/boot` | GPT + ext4 `/boot` | MBR + 自建 `PARM` |
| 依赖 Android | **无** | 部分（vendor LOADER/BL3X 格式） | **有**（mtdparts 坐标、trust 格式） |
| 官方源码对应 | radxa `binman-atf-mainline` | ophub 私有打包脚本 | family 默认 `only-blobs` + 自定义 hook |

**关键判读**：`only-blobs` 虽是 armbian family 对 rk3399 的**默认 scenario**，但它产出
的是 vendor 格式 `uboot.img`/`trust.bin`，落地坐标 64/16384/24576 —— 与
**官方已验证能起系统的 rockpi4b 板级配置不是一回事**。不能拿「family 默认」当
「官方成功基线」。

### 5.1b 从 WF7000A 实盘 rootfs 直接读到的启动参数（最关键的行为印证）

全盘流式搜 `wf7000a-armbian-full.img`（debugfs 读截断 ext4 失败，改用字符串命中）：

| 偏移 | 内容 | 含义 |
|---|---|---|
| `0x8a7d44` | U-Boot 内嵌 env `fdtfile=rockchip/rk3399-rock-pi-4b.dtb` | 官方 rockpi4b 原值，在 u-boot.bin 里 |
| `0x91bf01b` | `/boot/armbianEnv.txt`：`verbosity=1` / `bootlogo=false` / `console=both` / `overlay_prefix=rockchip` / **`fdtfile=rockchip/rk3399-wf7000a.dtb`** / `rootdev=UUID=...` / `rootfstype=ext4` | **WF7000A 刷完官方镜像后只改了 fdtfile 一个值**，引导链一行未动 |
| `0x8ff73e6c` 等 | `/boot/boot.cmd` 结尾 `booti ${kernel_addr_r} ${ramdisk_addr_r} ${fdt_addr_r}` | 经典 boot.scr 路线，与官方 rockchip64 一致 |

⇒ 本项目 `BOOT_FDT_FILE="rockchip/rk3399-mid.dtb"` 与 WF7000A 的成功做法**逐字对应**；`console=both` 是 armbian 默认值，故 csc 不需要 `SRC_CMDLINE` 覆盖（旧版自定义 `console=ttyS2,1500000n8 console=tty0` 反而偏离官方）。

**加载顺序要点**：board file 先 `source` radxa conf（设 `DDR_BLOB=v1.30` / `BOOT_SCENARIO=binman-atf-mainline`），family 的 `DDR_BLOB="${DDR_BLOB:-v1.25}"` 与 `BOOT_SCENARIO="${BOOT_SCENARIO:=only-blobs}"` 因已有值不覆盖，`post_family_config__radxa_rk3399_uboot` 再补 `UBOOT_TARGET_MAP`/ATF。⇒ **不要**在 csc 里再写 `BOOT_SCENARIO="only-blobs"` 或自定义 `write_uboot_platform()`。
`BOOT_SOC` 官方靠 `expr` 推导，本机 BSD `expr`（不支持 GNU `\+`）实测返回空，故 csc 显式写 `BOOT_SOC="rk3399"` 消除实现差异；不影响 DDR blob 版本。

### 5.3 验证顺序（路径 1 判据）

1. **编译期**：CI 通过新增硬校验 ⇒ 产物与官方 rockpi4b 的引导锚点同构（IDB@64 / FIT@16384 / MBR p1@32768，无 vendor 容器）。
2. **实刷**：短接进 MaskROM → `db rk3399_loader_v1.30.130.bin` → 整盘 `wl 0 <image>`（或按官方 `dd bs=32k seek=1` 只写引导区）→ 拔 OTG 断电冷启 → TTL 抓 `DDR Version 1.30` → `U-Boot` → `Starting kernel`。
   - 注意 Loader 逻辑 LBA = 物理 LBA + 8192 的偏移纪律；在 MaskROM 下写盘用物理坐标。
   - 原厂安卓整盘 `rescue/rk3399-mid-emmc-full-20261110.img` 是回滚兜底。
3. **失败分流**：若 BootROM 优先执行 eMMC boot0 硬件分区里的 vendor miniloader（`EXT_CSD[179]` 未读、11-10 原盘 LBA64 全零却能起安卓），会绕过 user LBA64 的 mainline IDB ⇒ 先读 `EXT_CSD[179]` / 清 boot0，再重试一次；仍失败才进入下方路径 2。

### 5.4 路径 2（**仅备案，本轮不实施**）

触发条件：路径 1 的**编译产物结构正确**、且已排除「boot0 抢占 / OTG 拉进 rockusb / 短接不彻底 / DTB 缺失」等外部因素后，**多次实刷仍无法走到 U-Boot**。此时才推断「ophub 采用混搭（IDB@64 + `LOADER`@16384 + `BL3X`@24576 + GPT）是为规避官方 mainline 写法在本类板上的引导障碍」，切换方式：以 `docs/ophub-固件选型.md` §十六的 r432 AIO-3399C 为模板，恢复 vendor `LOADER`/`BL3X` 容器 + 4 段 `stock/trust.img`，并按 `tools/mk-parm-variant.py` 的 PARM 逻辑处理 LBA0。**在此之前不得把 ophub 布局当作基线。**
