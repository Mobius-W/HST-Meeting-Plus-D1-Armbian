# RK3399 (rk3399-mid) 原厂 HAL — ES8316 声卡 Speaker 播放控件逆向报告

分析对象：`/tmp/hw-hunt/audio.primary.rk30board.so`（127KB，stripped）
目标：挖出原厂 Android 在 **speaker 播放**时对 `es8316-sound` 声卡实际下发的 ALSA kcontrol 及值。

---

## 0. 结论先行（TL;DR）

**原厂 HAL 对 ES8316 走的是"枚举路径"（enum path）方案，几乎不直接下发具体 volume/switch 数值。**

- Speaker 播放时，唯一实际下发的 kcontrol 是：**`Playback Path` = `SPK`**（枚举字符串），这与 `mixer_paths.xml` 完全一致。
- HAL 内 `es8316_speaker_normal_controls` 及其所有 `es8316_*_normal/ringtone/voip/..._controls` 数组**全部为空**（size=0，共享哨兵 0x18510）。
- `es8316_config_table` 34 个条目里，**所有播放类条目（含 speaker_normal）的控件数组 cnt=0**；只有 2 个 mic capture 条目指向真实数组。
- 那些看起来像"speaker 音量/开关/Class D Ratio"的具体数值（`Speaker Playback Volume=22/31`、`Class D SPK Ratio Control=10`、`Ext Spk Switch=1` 等）**属于 RK616 / RT3224 / RT3261 / RT5616 / WM8960 等其它 codec 的控件表，与 ES8316 无关**。
- **对你排查的指导意义**：原厂无声问题的另一端不在 HAL 数值 —— ES8316 的全部路由/增益/功放配置封装在 vendor 内核 es8316 驱动里（收到 `Playback Path=SPK` 后由驱动内部完成）。mainline 换成 `es7134` dummy codec 后，这个枚举控件及其背后的一切都没了，所以**无法靠"复刻 mixer 值"解决**，必须从 codec/DTS/驱动层面对齐（见文末建议）。

## 2. 逆向方法与关键结构

字符串 `es8316_speaker_normal_controls` 位于 `.dynstr`（是**动态符号名**，不是 rodata 普通字符串），因此直接从 `.dynsym` 读取符号值即可定位控件表，无需 XREF猜测。但APS2 打包重定位把大量数据指针在文件里置 0，我实现了 APS2 解码器（`/tmp/hw-hunt/aps2.py`，按 LLVM/bionic 格式：APS2 + SLEB128 总数/初始偏移 + 分组，标志位 1=GROUPED_BY_INFO/2=GROUPED_BY_OFFSET/4=GROUPED_BY_ADDEND/8=HAS_ADDEND），还原出运行时指针后逐表 dump。

### 2.1 config table 条目结构（16 字节/项）

```
struct config_entry {
    u32 word0;        // 索引/路由相关标志
    u32 word1;        // 0 或 1
    void *controls;   // 指向控件数组；0x18510 = 共享空数组哨兵
    u32 count;        // 控件个数 = 符号 size / 16
};
```

- 所有 `*_config_table` 均为 544 字节 = **34 项**。
- 条目索引语义（用 `default_config_table` 反推，已逐一验证）：

| idx | 含义 | idx | 含义 |
|---|---|---|---|
| e00 | **speaker_normal** | e14 | headset_normal |
| e01 | speaker_incall | e15..17 | headset incall/ringtone/voip |
| e02 | speaker_ringtone | e18..20 | bluetooth normal/incall/voip |
| e03 | speaker_voip | e21 | main_mic_capture |
| e04..07 | earpiece 系列 | e22 | hands_free_mic_capture |
| e08..13 | headphone / speaker_headphone 系列 | e23 | bluetooth_sco_mic_capture |
| — | — | e24..27 | playback/capture/incall/voip **off** |

### 2.2 控件条目结构（16 字节/项）

```
struct control {
    const char *name;       // off+0  控件名
    const char *enum_str;   // off+4  枚举值字符串(如"SPK")；数值控件时为 NULL(0)
    s32 value1;             // off+8  数值 / 左声道
    s32 value2;             // off+12 数值 / 右声道
};
```

反汇编 `set_controls`(0x11aa4) 证实：`r6` 以 `#0x10` 步进；`ldr r1,[r6,#-4]` 取 enum_str，`cbz` 判空——非空走 enum 设置（blx 0xd858），为 NULL 则 `ldrd r2,r1,[r6]` 取 value1/value2 走数值设置（blx 0xd8b8）。

### 2.3 顶层 card 映射（`.data` 0x25200 起）

```
{ "RKRK616",0x1b1b0 }, { "RKRT5616",0x1ee70 }, { "rockchiprt5651co",0x24270 },
{ "rockchipes8316c", 0x244b0 },  <-- ES8316 声卡 → es8316_config_table
{ "rockchipcx2072x",0x24750 }, ...   (未匹配 codec 名则回退 default_config_table)
```

## 3. 【核心答案】Speaker 播放时对 ES8316 声卡下发的控件清单

### 3.1 走 ES8316 专用表（`rockchipes8316c` → `es8316_config_table`）

| kcontrol | 值 | 依据 | 置信度 |
|---|---|---|---|
| （speaker_normal 播放类） | **无任何控件下发** | es8316_config_table e00 → controls=0x18510(共享哨兵), count=0 | 高 |
| `Differential Mux` | 0（main mic 路径） | e21 → es8316_main_mic_capture_controls，仅 capture 时 | 高（但非播放） |
| `Differential Mux` | 1（hands-free mic 路径） | e22 → es8316_hands_free_mic_capture_controls，仅 capture 时 | 高（但非播放） |

> 即：在 ES8316 专用配置下，speaker 播放 **HAL 不下发任何 ALSA mixer 控件数值**。

### 3.2 走默认表 / mixer_paths.xml（实际可听到的设置）

| kcontrol | 值 | 依据 | 置信度 |
|---|---|---|---|
| **`Playback Path`** | **`SPK`**（枚举） | `default_speaker_normal_controls`(0x19990) e00 + `mixer_paths.xml` path "speaker"；enum 值串在 0x1642c="SPK" | **高** |
| `Playback Path` | `OFF`（初始化/播放关闭时） | mixer_paths.xml 初始 ctl + `default_playback_off_controls` | 高 |
| `Capture MIC Path` | `MIC OFF`（初始化） | mixer_paths.xml 初始 ctl | 高 |
| `Voice Call Path` | `OFF`（初始化） | mixer_paths.xml 初始 ctl | 高 |
| `Voip Path` | `OFF`（初始化） | mixer_paths.xml 初始 ctl | 高 |

板子上 `mixer_paths.xml` 的 `"speaker"` 路径内容（SSH 实读确认）：

```xml
<path name="speaker">
  <ctl name="Playback Path" value="SPK" />
</path>
```

**这就是原厂 speaker 播放的全部 mixer 操作。** 板子 `/etc` 下无其它 es8316/volume/ratio 配置文件（已 grep 全等确认）；无独立内核模块，codec 驱动编译进内核。

### 3.3 `Playback Path` 枚举全集（HAL 中出现的取值）

| 值 | 出现路径 | 字符串地址 |
|---|---|---|
| `SPK` | speaker / speaker_incall / speaker_voip | 0x1642c |
| `HP_NO_MIC` | headphones | — |
| `RCV` | earpiece / receiver | 0x16453 |
| `BT` | bluetooth | — |
| `RING_SPK` | ringtone | 0x16440 |
| `OFF` | playback-off | — |

### 3.4 `Class D SPK Ratio Control` 默认值（任务 3）

| 项 | 结论 | 置信度 |
|---|---|---|
| 默认值 | **10**（f2=10, f3=0） | 高 |
| 归属 | **RT3224 / RT3261 的 speaker 控件表**（如 rt3224_speaker_normal_controls e14、rt3261 e14），共 17 处，值全部=10 | 高 |
| 是否 ES8316 | **否** —— es8316 表里无此控件 | 高 |

## 4. 兜底清单：其它 codec 的 speaker 控件（供对照，**非 ES8316**）

任务 4 要求整理所有"控件名+合理数值"。以下为各 codec `speaker_normal_controls` 的关键值。**注意这些不适用于你的 ES8316/ES7148 硬件，仅作参照。**

| 控件 | 值 | 所属 codec |
|---|---|---|
| `Speaker Playback Volume` | 22 / 22 | RK616 speaker_normal（ringtone 为 31/31） |
| `Speaker Playback Volume` | 120 / 120 | WM8960 speaker_normal |
| `Speaker Playback Volume` | 31 / 31 | RT3224 / RT3261 speaker_normal |
| `Headphone Playback Volume` | 31 / 31 | RK616 / RT3224 / RT3261；WM8960=116 |
| `Mono DAC Playback Volume` | 175 / 175 | RT3224 / RT3261 / RT5651 |
| `DAC1 Playback Volume` | 175 / 175 | RT5651 等（**非** es8316） |
| `Class D SPK Ratio Control` | 10 | RT3224 / RT3261 |
| `Ext Spk Switch` | 1（earpiece/speaker）/ 0（headphone/headset） | RK616 |
| `Speaker Playback Switch` | 1 / 1 | RK616 speaker_normal |
| `SPK GPIO Control` | "High" | RK616 speaker_normal |

ES8316 自身只有 2 个真实控件数组，且都是 capture：`Differential Mux` = 0 / 1。

## 5. 对 mainline 无声问题的推断（重要）

1. **原厂方案本质**：vendor 内核有一个名为 es8316 的 codec 驱动（尽管实物是 ES7148 纯 DAC + HT4832）。它向上的 ALSA 接口只暴露少量**枚举控件**（`Playback Path`/`Capture MIC Path`/`Voice Call Path`/`Voip Path`）。HAL 只需 `set("Playback Path","SPK")`，驱动内部完成 DAC 使能、输出路由、Class-D 增益、功放时序等所有寄存器操作。**HAL 里没有可直接抄的 volume/switch 数值表**——这就是"HAL 里挖不到具体 mixer 值"的根本原因。
2. **mainline 为何无声**：你换成 `es7134` dummy codec + simple-card，`amixer controls` 为空，等于把上述枚举控件及其背后的驱动逻辑整个丢掉了。MCLK 12.288MHz、I2S 双声道、功放 GPIO 常开只是物理层条件，缺少 codec 侧的输出使能/路由配置，模拟侧自然无声。
3. **可操作方向**（按优先级）：
   - 找回/移植 vendor es8316 驱动（保留 `Playback Path` 枚举控件），在 mainline 用真实 es8316 或兼容驱动，而不是 es7134 dummy。
   - 若坚持 dummy codec：需自行在驱动里实现 I2S→DAC 数据到 speaker 输出的路由，并确认 ES7148 的左/右对齐格式、LRCK/BCLK/MCLK 极性（es7134 默认参数可能与 ES7148 不匹配，尤其 `format=i2s` vs 左对齐、`mclk-fs`）。
   - HT4832 耳机功放需 I2C 初始化（原厂由驱动完成），mainline 若无驱动同样无声。
   - `rockchip,playback-channels=8` 与双声道播放的通道映射也需核对。
4. **结论**：**无法通过复刻 HAL 的 mixer 值让 mainline 出声**，因为原厂 speaker 播放对 ES8316 唯一的下发就是 `Playback Path=SPK` 这一个枚举动作，其效果的实现在 vendor 内核驱动内部。

## 6. 置信度汇总

| 结论 | 置信度 | 依据强度 |
|---|---|---|
| ELF 为 32-bit ARM | 确定 | ELF header + objdump |
| es8316 播放控件数组全空、e00 cnt=0 | 高 | 符号 size=0 + config table 静态解析 + APS2 重定位还原 + 反汇编交叉验证 |
| speaker 播放=`Playback Path=SPK` | 高 | default 表 + mixer_paths.xml（板子实读）双证据 |
| Class D Ratio=10 属 RT 系非 ES8316 | 高 | 17 处控件表归类 |
| 其它 codec speaker 音量值 | 高 | 控件表直接 dump |
| vendor es8316 驱动内部完成路由（推断） | 中 | 基于 HAL 侧无数值 + 实物无 I2C 的合理推断，未直接读内核驱动源码 |
