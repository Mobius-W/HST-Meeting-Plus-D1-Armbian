# RK3399 (rk3399-mid) vendor 内核 ES8316 / ES7243 驱动逆向报告

> 日期：2026-11-19
> 任务性质：**只读研究**。未修改任何系统文件、未刷机、未动板上系统。
> 素材：`stock/kernel.img`（24 MiB）、`armbian/rk3399-mid-stock.dts`、三篇既有文档。
> 工具：`python3` + `capstone 5.0.7` + `/usr/bin/objdump`（本机无 binwalk / 无 aarch64-linux-gnu-objdump）。
> 分析方法：识别容器 → 定位 ARM64 Image → kallsyms 建立 VA↔文件偏移映射 → ADRP/ADD XREF 定位驱动 → capstone ARM64 反汇编。
> 所有脚本落在 `/tmp/rkrev/`（临时、非系统）。

## 0. 结论先行（TL;DR）

| 问题 | 结论 | 证据等级 |
|---|---|---|
| kernel.img 是什么格式 | **Rockchip `KRNL` 私有头 + 未压缩 ARM64 Image**，头 8 字节，真正的 Image 从第 8 字节开始；与 `boot.img` 内 kernel 负载仅差这 8 字节头 | **实测** |
| 如何解包 | `tail -c +9 kernel.img > Image`（或按 `boot.img` page=0x4000 抽 kernel），得到 Linux 4.4.83 ARM64 Image | **实测** |
| VA↔文件偏移映射 | `VA = 文件偏移 + 0xffffff8008000000`（`_text`=0xffffff8008080000 在文件 0x80000；kallsyms_addresses 交叉验证） | **实测** |
| vendor es7243 是否有 0x00 CSM_ON 写 | **没有**。startup 写序列 11 条里不含 0x00；全驱动也搜不到对 0x00 的立即数写 | **实测（反汇编 + 全镜像模式扫描）** |
| 是否碰 0x0D CHIP STATE | **没有**。startup 11 条 + standby 4 条都不含 0x0D | **实测** |
| 原厂 11 写序列 | 反汇编逐字节还原，与既有文档**完全一致**：`06=18,01=0c,02=10,03=04,04=02,05=1a,08=41,07=80,09=00,06=00,05=13` | **实测** |
| ★ 新发现：0x12 芯片的 08 寄存器特例 | startup 循环里有一处分支：当 `i2c_addr==0x12` 且循环下标==6 时，把第 7 条从 `08=41` 改成 **`08=21`**（增益差异，与既有文档一致，但此处首次拿到**代码级证据**） | **实测** |
| standby 序列 | `06=05,05=1b,06=5c,09=9f`（4 条），与文档一致 | **实测** |
| 采样率→码映射 | hw_params 把 32k/44.1k/48k/88.2k/96k/176.4k/192k 映射成一个 4-bit 码（3/0/2/8/a/c/e）；其它率返回 -EINVAL。最后统一调用 helper `w1=0x8621,w2=0xf,w3=码`（该写非 ES7243 寄存器，目标 regmap 未确证） | **实测** |
| kcontrol "Playback Path"/"Capture MIC Path" | **本内核镜像里完全没有这些字符串**（`grep` 全镜像 0 命中）。vendor es8316 用的是标准 ES8316 控件名（"Differential Mux"/"Line input PGA"/"Left Hp mux"…），不是 path 枚举 | **实测** |
| ES7148 format/mclk-fs/lrck 极性 | **未在 es8316/es7243 驱动中找到直接配置**；仅有 `simple-audio-card,mclk-fs` 的解析代码（通用 machine driver）。ES7148 是纯 I2S DAC，无寄存器，相关极性只能来自 DTS/I2S 控制器侧 | **实测（未找到）+ 推断** |

**一句话**：vendor es7243 驱动的操作与既有文档记录**高度吻合**，没有隐藏的 0x00/0x0D 魔法写；这进一步坐实"软件侧已穷尽、问题在模拟/硬件层"的判断。同时**反证了一个前提**——vendor 内核里并不存在 HAL 所用的 `Playback Path=SPK` 枚举控件，说明 path 枚举是在 **HAL 层或另一个 machine 层**实现的，而非这个 codec 驱动。

## 1. kernel.img 格式识别与解包（可复现）

### 1.1 识别过程

`file` 只报 `data`。逐 magic 检测：

```
偏移 0x00: 4b 52 4e 4c = "KRNL"      <- Rockchip 私有 kernel 头
偏移 0x04: 08 70 19 01 = 0x01197008 = 18444296  <- kernel 负载长度
偏移 0x08: 00 40 3e 14 = 0x143e4000
偏移 0x10: 00 00 08 00 = 0x80000    <- ARM64 text_offset
```

对照 `boot.img`（标准 Android boot.img）：

```
magic = "ANDROID!"
kernel_size = 18444296 (= 0x01197008, 与 KRNL 头里的 size 完全相同)
kernel_addr = 0x60408000
page_size   = 16384 (0x4000)
```

**结论**：`kernel.img` = `"KRNL"` + 4 字节 size + `boot.img` 的 kernel 负载（负载前 8 字节 = `0x143e4000,0`，这是 Rockchip 在 Image 前加的 head stub）。`kernel.img` 总长 0x1800000，是被填充到 24 MiB 的分区镜像；有效 kernel 只有 0x01197008 ≈ 17.6 MiB。

### 1.2 解包命令（实测可复现）

```bash
KIMG=/Volumes/HDD/WorkBuddy/HomeDev/rk3399-mid-backup/stock/kernel.img
BOOT=/Volumes/HDD/WorkBuddy/HomeDev/rk3399-mid-backup/stock/boot.img

# 法 A：从 kernel.img 去掉 8 字节 KRNL 头
tail -c +9 "$KIMG" | head -c 18444296 > /tmp/rkrev/Image.from-kernel

# 法 B：从 boot.img 按 page_size=0x4000 抽 kernel
dd if="$BOOT" of=/tmp/rkrev/Image.from-boot bs=4096 skip=4 count=$((18444296/4096+1)) \
   iflag=skip_bytes,count_bytes 2>/dev/null
# 更稳妥用 python 切片：data[0x4000:0x4000+18444296]
```

镜像是**未压缩**的（`strings` 能直接读到 `Linux version 4.4.83 (wang@wan-qitianm425-n000) ... #14 SMP PREEMPT Fri Sep 20 17:33:36 CST 2019`，文件偏移 `0xa90078`），故无需 gzip/lz4 解压；全镜像扫描 gzip/lz4/zstd magic 均为误报或无关。

> 说明：标准 ARM64 Image magic `0x4d4d5648` 在镜像里**不存在**（Rockchip 用 `0x143e4000` head stub 取代），所以不能靠 magic 定位，改用 kallsyms + 字符串 XREF（见 §2）。

### 1.3 虚拟地址映射（校准）

- kallsyms_addresses 数组在文件 `0xbc8908`，共 **105989** 项（`kallsyms_num_syms`=0x19e05 在 `0xc97a08`），首项 = `0xffffff8008080000` = `_text`。
- 异常向量表在文件 `0x1000`（可见 `msr icc_dir_el1` / `icc_eoir1_el1`），符合 `_text+0x1000`。
- 自引用 `adr x1, #...844074` @ 文件 `0x84406c` 反推同一基址。

⇒ **`VA = 文件偏移 + 0xffffff8008000000`**，全文所有 VA 均按此换算回文件偏移（报告里一律给文件偏移，便于 `xxd`）。

## 2. 驱动代码定位方法（可复现）

1. `strings -a -t x kernel.img | grep -iE 'es8316|es7243|spk_con|amp_en'` 拿文件偏移：
   - es7243 相关：`0xbad3e0`(es7243_i2c_probe)、`0xbad438`("everest,es7243")、`0xbad588`(es7243_init_mode)、`0xbad5a0`(es7243_startup)、`0xbad5c8`(es7243_set_standby)、`0xee7991`("es7243")、`0xf789da/e9/f5`(es7243_standby/init/start 符号名串)。
   - es8316 相关：`0xee6010`("amp-en-gpio")、`0xee72ed`("spk_con_gpio")、`0xee5d57`("spk-con-gpio")、`0xee6088`(es8316_interrupt)、`0xee60b8`("ES8316 HiFi")。
2. 写 ADRP/ADD 扫描器（`/tmp/rkrev/xref*.py`）：扫 AArch64 `adrp`+`add`，在**文件偏移空间**直接算目标页/偏移（因为 VA 基址页对齐，`adrp` 的页相对关系在文件偏移里成立），得到对字符串/数据表的代码 XREF。
3. capstone `CS_ARCH_ARM64` 逐函数反汇编（`/tmp/rkrev/disasm.py`、`batch.py`），分支目标减 VBASE 换回文件偏移。

## 3. ES7243 vendor 驱动逆向结果（实测）

### 3.1 关键数据表（文件偏移，原始字节）

| 偏移 | 字节 | 含义 |
|---|---|---|
| `0xbad5a0` | `"es7243_startup\0"` | 函数名串（紧邻其表） |
| **`0xbad5b0`** | `06 18 01 0c 02 10 03 04 04 02 05 1a 08 41 07 80 09 00 06 00 05 13` | **startup 写表，11 对 (reg,val)** |
| `0xbad5c8` | `"es7243_set_standby\0"` | 函数名串 |
| **`0xbad5e0`** | `06 05 05 1b 06 5c 09 9f` | **standby 写表，4 对** |
| `0xbad5e8` | `"es7243\0"` | 名字串 |

startup 表按 (reg,val) 拆：

| # | reg | val | 说明 |
|---|---|---|---|
| 0 | 0x06 | 0x18 | STATE CONTROL |
| 1 | 0x01 | 0x0c | SDP / 格式 |
| 2 | 0x02 | 0x10 | LRCK divider |
| 3 | 0x03 | 0x04 | BCLK divider |
| 4 | 0x04 | 0x02 | ADC clock div |
| 5 | 0x05 | 0x1a | MUTE control（→ 后被 0x13 覆盖） |
| 6 | 0x08 | 0x41 | **增益（0x12 芯片特例改 0x21）** |
| 7 | 0x07 | 0x80 | ANALOG CTRL0 |
| 8 | 0x09 | 0x00 | ANALOG CTRL2 |
| 9 | 0x06 | 0x00 | STATE CONTROL 清零 |
| 10 | 0x05 | 0x13 | MUTE control 恢复 |

⇒ 与既有文档 `麦阵-ES7243驱动-进展与待办-20261116.md` §2.2 的 11 写序列**逐字节一致**。

### 3.2 startup 函数的反汇编证据（文件 `0x842dc8`–`0x842eac`）

```
0x842e08: add  x19, x19, #0x1d1        ; x19 = 0xbad3d8+0x1d1 → 指向写表区
0x842e0c: mov  w21, #0                 ; 循环下标 i=0
0x842e18: mov  w25, #8                 ; 0x12 特例所用 reg=0x08
; ---- loop ----
0x842e20: cmp  w21, #6
0x842e24: b.ne 0x842e40
0x842e28: ldrh w0, [x20, #2]           ; 取 i2c client 的 addr（低 8 位=0x10/0x12）
0x842e2c: cmp  w0, #0x12
0x842e30: b.ne 0x842e40
0x842e34: strb w25, [x29, #0x50]       ; ★ addr==0x12 且 i==6: reg=0x08
0x842e38: mov  w0, #0x21               ; ★ val=0x21（覆盖 0x41）
0x842e3c: b    0x842e4c
0x842e40: ldurb w1, [x19, #-1]         ; 常规: reg = table[2i]
0x842e44: ldrb  w0, [x19]              ;       val = table[2i+1]
0x842e48: strb  w1, [x29, #0x50]
0x842e4c: strb  w0, [x29, #0x51]
0x842e50: add  x1, x29, #0x50          ; buffer = {reg,val}
0x842e54: mov  x0, x20                 ; i2c_client
0x842e58: mov  w2, #2                  ; len=2
0x842e5c: bl   0x669394                ; i2c 写 2 字节
0x842e60: cmp  w0, #2
0x842e64: b.eq 0x842e78
0x842e68: ldurb w2, [x19, #-1]
0x842e6c: mov  x0, x24 / mov x1, x22   ; 错误分支 dev_err(... "0x%0x -- 0x%0x\n")
0x842e74: bl   0x49322c
0x842e78: add  w21, w21, #1
0x842e7c: add  x19, x19, #2            ; 前进一对
0x842e80: cmp  w21, #0xb               ; ★ 共 11 次
0x842e84: b.ne 0x842e20
```

**要点（实测）**：
- 循环上限 `0xb` = 11 次 ⇒ 11 条写。
- `0x669394` 反汇编确认是 `i2c_smbus`-风格：在栈上拼 `i2c_msg`（`strh` addr、`strh len=2`、`buf={reg,val}`），调用 `0x669308`（`i2c_transfer`）。即每条是 **1 字节寄存器地址 + 1 字节值**。
- 唯一的条件分支就是 `addr==0x12 && i==6 → 08=0x21`；**没有任何分支写 0x00 或 0x0D**。
- 循环后紧接一段 15 次（`cmp w19,#0xf`）的读回/校验循环（`0x842e88`–`0x842ec0`，读字符串 `0xee7979` "0x%0x -- 0x%0x\n" 做 dump），是调试打印，非配置写。

> 指针算术备注：`x19` 由 `0xbad000 +0x3d8 +0x1d1 = 0xbad5a9` 起读 `[x19-1]/[x19]`；静态推得的表基与 `0xbad5b0` 相差 8 字节（落在相邻的 "es7243_startup" 名字串里）。**写表的字节内容与 11 次循环 + 0x12 特例在语义上完全自洽**（i=6 正好对到 `08 41`），因此表内容可信；起始指针的 8 字节偏差可能是我对某个中间 `add`/重定位的静态还原误差，标注为**推断**。

### 3.3 standby 序列

表在 `0xbad5e0`：`06=05, 05=1b, 06=5c, 09=9f`。函数符号名 `es7243_set_standby` 在 `0xbad5c8`、`es7243_standby` 在 `0xf789da`。与文档一致。

### 3.4 采样率 / 格式配置（hw_params，文件 `0x8427b8`–`0x8428ac`）

函数入口 `0x8427b8` 读 `w4 = params->rate`（`[x1,#0x128]`），按采样率分支产生一个 4-bit 码 `w3`：

| 采样率（常量） | Hz | 码 w3 | 分支 |
|---|---|---|---|
| `0x7d00` | 32000 | **3** | `0x842800`→`0x84288c` |
| `0xac44` | 44100 | **0** | `0x8427e8`→`0x842848` |
| `0xbb80` | 48000 | **2** | `0x8427f4`→`0x842894` |
| `0x15888` | 88200 | **8** | `0x8427c4`→`0x842850` |
| `0x17700` | 96000 | **0xa** | `0x842830`→`0x842840` |
| `0x2b110` | 176400 | **0xc** | `0x842810`→`0x842858` |
| `0x2ee00` | 192000 | **0xe** | `0x842820`→`0x842860` |
| 其它 | — | 返回 -0x16 (EINVAL) | `0x842868`→dev_err |

分支用 `b.hi`/`b.eq` 把 <88200 与 >88200 分开（见 `0x8427d8`–`0x8427e4`）。

最后统一下发（文件 `0x842898`–`0x8428a0`）：

```
0x842898: mov w1, #0x8621
0x84289c: mov w2, #0xf
0x8428a0: bl  0x83a1e8       ; helper: x0+0x50 → 0x83a180
```

⇒ **8k/16k 不在此函数支持列表**（非上述 7 种率走 `0x842868` 返回 -EINVAL）。这是**实测**的反汇编常量。
但 `w1=0x8621` 作为 16-bit "寄存器/参数" 已超出 ES7243 的 0x00–0x0D 寄存器空间，故这次写**不是**对 ES7243 寄存器的写。（**11:13 更正**：继续反汇编 helper 后确认——`0x83a1e8` 仅 `x0+=0x50` 后尾调用 `0x83a180`，后者从 `[x0+0x78]` 取 ASoC widget/component 对象，经 `0x4b34d4→0x4b1f38→0x4b1d14` 的 **regmap 读改写框架**（`blr [obj+0x170]`/`[obj+0x190]`）；`0x8621` 全镜像仅此 1 处、es7243 代码区内 0 次作为数据；该函数还引用 `dif-out` DAI 名并紧邻 `snd_tc358749x_dai_hw_params` 数据区 ⇒ **归属未坐实，很可能不是 es7243**。因此不能把 `0x8621` 当作可抄到 mainline 的 ES7243 寄存器写；本条从"线索"降为"存疑观察"。）

### 3.5 probe（文件 `0x842be0`–`0x842d58`）

- 从 DT 解析 `reg`/地址（读到 2 字节 addr，与 `0x10`/`0x12` 比较，见 `0x842c10 cmp w2,#2`）。
- 用 `0xee7000+0x939 = "x-audio"` 之类的 dev_err 串报错。
- 把 client 挂到全局数组 `0x928e000+0xd28`（`0x842cb0` 的 `str x21,[x2,w0,sxtw #3]`），即**两颗 ES7243 注册进一个全局 list**，由 es8316/machine 侧统一 start/standby（与既有文档"es8316 统管采集"结论一致，**实测**）。

## 4. ES8316 魔改驱动 / GPIO 时序（实测 + 明确标注推断）

### 4.1 ★ 最重要的反证：没有 path 枚举控件

全镜像精确搜索：

```
"Playback Path"    : 0 命中
"Capture MIC Path" : 0 命中
"Voice Call Path"  : 0 命中
"Voip Path"        : 0 命中
"Main Mic"         : 0 命中
"HP_NO_MIC"/"RING_SPK": 0 命中
```

而标准 ES8316 控件名大量存在（`"Differential Mux"`@0xee60d1、`"Line input PGA"`@0xee60f6、`"Left Hp mux"`@0xee61fc、`"Playback Polarity"`@0xee6358、`"Speaker L Playback"`@0xee6f46 等）。

⇒ **结论（实测）**：本 vendor 内核的 es8316 驱动**不实现** HAL 所用的 `Playback Path` 枚举。既有 HAL 文档里"下发 Playback Path=SPK"是真的（HAL 侧/mixer_paths.xml），但那个控件的**实现端不在本内核的 es8316 codec 驱动里**。可能位置（**推断**）：
1. HAL 直接操作功放/GPIO（不经过 ALSA kcontrol），或
2. `Playback Path` 由某个 loadable module / 厂商 patch 提供（不在本 kernel.img），或
3. 控件字符串在编译期被拼接/来自另一个 so，内核侧只用标准 ES8316 控件名。

这对 mainline 移植的含义：**不能指望从本内核找到"收到 Playback Path=SPK 后拉 GPIO"的处理函数**——它不在这里。

### 4.2 es8316 probe 里的 GPIO 获取（实测，文件 `0x83e440`–`0x83e600`）

```
0x83e464: adrp x1, 0xee6000 ; add x1,x1,#8   -> "bt-sco-pcm"  (DAI名字, 非GPIO)
0x83e488: adrp x1, 0xee6000 ; add x1,x1,#0x14 -> "en-gpio"    (错误串 "Can not read ... en_gpio")
0x83e4dc: adrp x1, 0xee7000 ; add x1,x1,#0xad0 -> "io-card,hp-det-gpio" (machine 层串, 非本驱动)
0x83e5c8: adrp x1, 0xee6000 ; add x1,x1,#0x91 -> "...interrupt" (request_irq 失败串)
```

 GPIO 属性名字符串确实存在：`"amp-en-gpio"`@`0xee6010`、`"spk_con_gpio"`@`0xee72ed`、`"spk-con-gpio"`@`0xee5d57`，并有错误串 `"Can not read property amp_en_gpio"`@`0xee601c`、`"Failed to request amp_en_gpio"`@`0xee603f`。

- `0x83e478` / `0x83e4f0` 调用 `0x33277c`（带 `con_id` 字符串 + `&x29,#0x44` 输出参数）⇒ 是 `devm_gpiod_get`/`of_get_named_gpio` 类函数，把 GPIO 存进 `x19+0xac`（hp/amp-en）与 `x19+0xb0`（另一个 gpio）。
- 成功路径 `0x83e4cc`–`0x83e4d8`：`gpio_request`-like `0x33104c` 后 `0x3308e8`（`gpiod_direction_output(gpio, 1)`，**w1=1**）⇒ probe 阶段有"方向输出且置 1"的动作（**实测到 mov w1,#1**，但无法静态证明它就是 amp-en 那一路；标注 **推断**）。
- `spk_con_gpio`（GPIO3 0x19）与 `amp-en-gpio`（GPIO3 0x05）的**运行时 set_value 顺序/延时**：在 es8316 驱动函数体内未定位到明确的 `gpiod_set_value(...,0/1)` + `mdelay` 序列（GPIO 操作经全局结构间接调用，静态追踪到 `0x33xxxx` 通用 GPIO helper 后失去直接 con_id 关联）。**这部分无法给出可信的"顺序+延时"结论，如实标注为未解**。

### 4.3 是否碰 I2C 0x11

es8316 驱动 rodata 里有 `"ES8316 HiFi"`@`0xee60b8`，且标准 ES8316 控件名齐全（说明这段代码本是**真·ES8316 驱动**），但 DTS 里 `es8316@11` 的 `clocks=<&cru 0x59>`、两个 GPIO 与"实物是 ES7148（无 I2C）"矛盾。

- 在 es8316 相关代码里**没有**找到针对 I2C 0x11 的具体寄存器写序列（大量 `0x70/0x71/0x72/0x73/0x80/0x86/0xfa` 写属于 `0x840000`–`0x841f00` 的 **rt5640/rt5651** 驱动区，非 es8316）。
- ⇒ **实测结论**：本 kernel.img 里的 es8316 驱动主要是"标准 ES8316 控件框架 + GPIO 探测"，不能证明它对 0x11 下发过让 ES7148 出声的配置。与既有文档"es8316 只是空壳/魔改、靠 GPIO 控制"一致。

## 5. ES7148 format / mclk-fs / LRCK 极性配置（实测未找到 + 推断）

- 全镜像搜 `mclk-fs` 只在通用 machine driver 解析代码里出现：`"simple-audio-card,mclk-fs"`@`0xee7ab6`（XREF `0x843798`）、`"mclk-fs"`@`0xee7abe`（XREF `0x843b08`）——这是 `asoc_simple_card` 的通用属性解析，**不是** ES7148 专属。
- ES7148 是 QFN-12 纯 I2S 输入 DAC，**无 I2C、无寄存器**（既有结论），因此"format=I2S/左对齐、mclk-fs、LRCK 极性"只能由：
  1. SoC I2S 控制器寄存器（`rockchip_i2s` 的 `SND_SOC_DAIFMT_*` → CKR），或
  2. DTS `daifmt`/`mclk-fs`/`bitclock-master` 属性
  决定。**vendor es8316/es7243 驱动里都不直接配置这些**（实测未找到）。
- 推断：原厂 DTS（非本反编译 DTS 所示的极简版）里 `es8316-sound` / i2s 节点应带 `daifmt = <SND_SOC_DAIFMT_I2S | ...>` 与 `mclk-fs=<256>`；mainline 侧需核对 `es7134` dummy codec 的 `daifmt` 与 `mclk-fs` 是否与之一致（与 HAL 文档 §5 建议相同）。

## 6. 对 mainline 移植的可操作结论

| 方向 | 结论 | 置信度 |
|---|---|---|
| ES7243 寄存器序列 | vendor 侧就是已知的 11 写 + standby 4 写，**无隐藏 0x00/0x0D 写**。mainline 已复刻 ⇒ 寄存器层面无需再改 | 高（反汇编逐字节） |
| 0x12 芯片增益 | 第 7 条 `08=0x21`（0x10 芯片 `08=0x41`），已有实现已区分 ⇒ 正确 | 高（代码分支） |

| 0x0D CHIP STATE 恒 0x60 | vendor 驱动**从不读/写 0x0D**，所以"恒 0x60"不是驱动配置问题 ⇒ 更支持硬件/模拟域未上电判断 | 高 |

| ES7148 音频格式 | 需从原厂 DTS/board 文件（非本极简反编译 DTS）或 I2S 控制器寄存器取证；本 kernel.img 不含相关信息 | 中 |

## 7. 证据 / 推断分级清单

**实测（反汇编或全镜像扫描，可复核）**
- kernel.img = KRNL 头 + 未压缩 ARM64 Image；VA 基址 0xffffff8008000000；Linux 4.4.83。
- kallsyms 105989 项；es7243 代码区文件 0x842000–0x846000。
- es7243 startup 表 0xbad5b0（11 对）、standby 表 0xbad5e0（4 对）、11 次循环、`addr==0x12&&i==6 → 08=0x21` 分支、`0x669394`=i2c 2 字节写。
- 采样率→4-bit 码映射（7 种率）+ 统一 helper 调用 `w1=0x8621,w2=0xf,w3=码`。
- probe 把两颗 ES7243 挂全局数组。
- 全镜像无 `Playback Path` 等 4 个 path 串；ES8316 标准控件名存在。
- es8316 probe 有 gpio 获取 + `gpiod_direction_output(...,1)`（mov w1,#1）。
- `mclk-fs` 仅出现在通用 simple-card 解析。

**推断（未在镜像中直接取得）**

- helper `w1=0x8621,w2=0xf,w3=码` 的目标 regmap / 位域语义（疑似时钟或 ES7148 侧，未确证）。
- `Playback Path` 实现端的三种可能位置（HAL / 独立 module / 字符串拼接）。
- es8316 `mov w1,#1` 的 GPIO 具体是哪一路（amp-en 还是 hp-det）。
- 功放 GPIO 的精确顺序与延时（**未解**）。
- 原厂 DTS 的 daifmt/mclk-fs 取值。
